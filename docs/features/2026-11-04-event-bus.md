# Event bus and conductor

Status: Building
Date: 2026-11-04

## Problem

A developer wants "when a pull request opens or merges, do this". HinaCode cannot express that today. Three services (`AutoArchive`, `PullRequestGuides`, `PullRequestWatcher`) each poll GitHub on their own timer, keep what they learned private, and act directly. Nothing remembers that a pull request was open three minutes ago, so "merged" does not exist as a fact anyone can react to. Each new reaction would mean another poller.

## User flow

1. In Settings, Automations, the developer creates an automation with the **Pull request** trigger and ticks **Opens**, **Merges** or **Closes without merging**. The checkboxes are reachable by tab and toggled with space, like the rest of the form.
2. The prompt uses `{{pullRequest.title}}`, `{{pullRequest.url}}`, `{{pullRequest.number}}`, `{{pullRequest.author}}`, `{{pullRequest.headRefName}}`, `{{pullRequest.baseRefName}}` and `{{topic}}`.
3. A thread in that project opens a pull request. The automation starts its own thread and the run shows up in the automation's history, as with every other trigger.
4. For an engineer, every reaction lives in one `switch` in `src/main/services/Conductor.ts`. Reading it answers "what happens when a pull request merges". Adding a reaction is one more line there.

## Design

### The bus

`src/main/services/EventBus.ts` is Effect's `PubSub`, typed and named. It borrows the useful half of [msgq](https://github.com/commaai/msgq).

| msgq                                    | EventBus                                                         |
| --------------------------------------- | ---------------------------------------------------------------- |
| Named endpoints                         | `topic` on a closed union, so a typo fails `pnpm typecheck`      |
| One publisher per endpoint              | A convention. Each topic is published from one service           |
| Ring buffer, publisher never blocks     | `PubSub.sliding(256)`                                            |
| Slow reader loses the oldest messages   | Same. The conductor drains at once, so the ring stays near empty |
| Readers track their own position        | Each `PubSub.subscribe` has its own                              |
| Bytes in shared memory across processes | Plain values in one process. HinaCode has no second process      |

It is separate from `Events`, which encodes `PushEvent`s for windows and remote clients. Bus events are internal and never cross a process boundary, so they carry no schema.

| Topic                | Published by           | Meaning                                                |
| -------------------- | ---------------------- | ------------------------------------------------------ |
| `pullRequest.linked` | `PullRequests.link`    | A row was inserted. Not repeated when linking again    |
| `pullRequest.opened` | `PullRequestLifecycle` | A linked pull request was created after its thread was |
| `pullRequest.merged` | `PullRequestLifecycle` | An observed pull request moved to merged               |
| `pullRequest.closed` | `PullRequestLifecycle` | An observed pull request closed without merging        |

Events are per link. A pull request linked to two threads publishes twice, because a reaction may care about the thread. The automation's existing `(automation_id, event_key)` unique index runs the prompt once and records the second as skipped.

### What "opened" means

HinaCode only knows pull requests linked to a thread, and `link` also runs when a thread checks out an old one. GitHub's `createdAt` settles it with no threshold. A pull request created after its thread began was opened by that thread's work. One created before it is an existing pull request being picked up, which publishes no `opened`. Someone else's pull request linked into an older thread counts as opened, which is an accepted false positive.

### The source

`PullRequestLifecycle` turns polling into transitions. Migration `0040_pull_request_observed_status` adds a nullable `observed_status` to `pull_request_link`.

- `null` means not observed yet. The first read records silently, so upgrading never replays history for existing links.
- `merged` and `closed` are settled and never read again, so the steady-state cost is one read per open linked pull request every three minutes. Reads go through `GitHub`'s batched, cached `PullRequestRead`, so a sweep mostly reuses what `AutoArchive` and the guides fetched.
- Archived threads still count. Archiving a thread and merging its pull request later is the common order.

The stored status also makes a restart correct. A pull request merged while the app was closed still moves from `open` to `merged` on the first sweep after launch.

`PullRequests.observe` updates the status inside a transaction and returns the previous value, or nothing when the status did not change or was already settled. The sweep and the `linked` reaction can race on one link, and only the caller that moved it publishes.

### The conductor

`src/main/services/Conductor.ts` subscribes first and starts the sweep second, so no event is published before it listens. Each event runs in its own fiber with failures logged, so a slow worktree setup or a failed reaction holds up nothing else.

```ts
switch (event.topic) {
  case "pullRequest.linked":
    return lifecycle.announce(event)
  case "pullRequest.opened":
  case "pullRequest.merged":
  case "pullRequest.closed":
    return automations.firePullRequest(event)
}
```

A plain `switch` gives an exhaustive compile error when a topic is added, which is everything a registry would have offered.

### The action

`AutomationTrigger` gains `{ type: "github.pullRequest", topics }`. It is event driven, so it has no poller and no cursor, and an automation never replays anything from before it existed. `firePullRequest` starts a run for each enabled automation in the source thread's project that lists the topic, with the event as the template payload and `topic:url` as the event key.

**Threads started by an automation never fire automations.** Without this, "on opened, do X" loops as soon as X opens a pull request, and the loop spends the developer's tokens with nobody watching. The rule is one line and makes cycles impossible. The cost is that automation pipelines cannot chain through pull requests.

### Trust boundaries

Nothing new crosses the network. Reads use the existing `GitHub` service and its schemas. A pull request title lands in a prompt the way an issue title already does for the `github.issue` trigger, and only pull requests the developer's threads linked can fire.

## Out of scope

- **Delivery across a crash.** The status is stored before the event is published, so a crash in that window loses the event. An outbox table would close it, but it is a queue we do not need yet, and the bus stays in memory like msgq's.
- **Reopened pull requests.** A closed pull request is settled, so reopening it and merging it later publishes nothing. Polling every closed link forever costs more than this edge is worth.
- **Moving `AutoArchive` and `PullRequestGuides` onto the bus.** `AutoArchive` is level triggered on purpose. It retries while a thread is busy, which one edge event cannot do. Guides also react to new pushes. Both need their own change.
- **Pull requests no thread linked.** Those need webhooks or a repository-wide poll.
- **Instant reactions to a merge clicked in HinaCode.** They wait for the next sweep, up to three minutes.

## Verification

- `PullRequestLifecycle.integration.test.ts` covers opened against thread age, a silent first observation, a merge publishing once, settled links never being read again, and racing observers.
- `Automations.integration.test.ts` covers the topic filter, project scoping, the automation-thread guard, the rendered prompt and the duplicate run.
- `Conductor.integration.test.ts` drives a real `PullRequests.link` through the bus and the lifecycle to the automation reaction, then a merge through the scheduled sweep.
- In the real app with `verify-hinacode`, a fake `gh` on `PATH` plays a pull request from open to merged. Create the automation in the form, link the pull request, flip it to merged, and see both runs in the automation history.
