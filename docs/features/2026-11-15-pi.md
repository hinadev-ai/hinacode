# pi

Status: Shipped
Date: 2026-11-15

## Problem

A developer who uses [pi](https://pi.dev) for its provider coverage, extensions and skills has to leave HinaCode to run it. They lose the worktree, approvals, pull request links and the parallel view of their other agents.

## User flow

1. The model picker has a pi tab. It lists the models pi can reach with the developer's logins, such as `anthropic/claude-opus-4-8` or `openrouter/qwen/qwen3-coder`.
2. A pi thread works like any other: streaming text and thinking, tool rows, file changes, approvals in Supervised and Auto, Stop, steering a running turn, compaction rows and the context meter.
3. The effort control shows the thinking levels pi offers for the model, `off` to `max`, and hides for a model without reasoning.
4. A pi extension that asks the user something (`ctx.ui.select`, `confirm`, `input`, `editor`) shows a question card in the thread.
5. When pi has no login for the model's provider, the turn fails with pi's own error and the hint to run `pi auth login`.
6. `pi --resume` in a terminal lists HinaCode's pi threads, because they share pi's session store.

## Design

pi has an RPC mode, `pi --mode rpc`, that speaks strict JSONL over stdio: commands in, responses and events out. It also loads extensions from a path with `-e`. HinaCode uses both.

**One process per turn.** pi starts in about 220 ms, so each turn runs its own process and ends it when the turn settles, like opencode. Nothing of pi runs between turns, so there is no `closeSession` or `warm`.

```
pi --mode rpc --approve -e <hinacode extension> \
   [--model <provider>/<id>] [--thinking <level>] [--session <id>] \
   --append-system-prompt <HinaCode instructions>
env HINACODE_MCP_URL, HINACODE_MCP_AUTHORIZATION, TMPDIR...
```

- `--approve` trusts the project's `.pi/` files, as importing a project trusts it (`docs/adr/0008-import-trusts-the-project.md`).
- The first turn omits `--session`. pi creates a session and the provider reads its id with `get_state`, then emits `session_bound`. Later turns pass `--session <id>`. pi exits with `No session found` when it is gone, and with `Session found in different project` when the thread's folder is not the session's. Either fails the turn with `sessionLost` rather than starting an empty session.
- The instructions go in `--append-system-prompt` on every turn, so pi keeps them across compaction.

**The HinaCode extension.** pi has no MCP flag and no approval prompts. A 30-line extension (`src/main/agents/pi/extension.mjs`) closes both gaps:

- It calls `pi.registerMcpServer("hinacode", { url, headers, timeout, exposure: "direct" })` from the two environment variables, so the credential never reaches argv or the user's `mcp.json`. pi names the tools `mcp__hinacode__<tool>`, the form HinaCode already labels.
- On `tool_call` it asks `ctx.ui.select("hinacode:approve <toolCallId>", ["allow", "deny"])` and returns `{ block: true, reason }` unless the answer is `allow`. Over RPC that arrives as an `extension_ui_request`. The provider, not the extension, decides: it answers at once from the thread's current access mode, or emits `approval_requested` and waits. A mode change therefore applies to the next tool call of a running turn.
- HinaCode ships the source as a string (`?raw`) and writes it to `hinacode.mjs` in a private temp directory that the provider creates at start and removes at shutdown. A fixed path under the shared temp directory would let another local user plant a file that pi loads.

| Access mode | Behavior            | Runs without asking               |
| ----------- | ------------------- | --------------------------------- |
| Supervised  | `askUnlessReadOnly` | `read`, `grep`, `find`, `ls`      |
| Auto        | `acceptEdits`       | the above plus `edit` and `write` |
| Full        | `bypass`            | everything                        |

Allow for session remembers the command for `bash` and the tool name for any other tool. HinaCode keeps that in memory for the thread until the app quits.

**Event mapping** (`src/main/agents/pi/events.ts`, pure):

| pi                                               | HinaCode                                                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `message_update` `text_delta` / `thinking_delta` | `text_delta` / `reasoning_delta`                                                                               |
| `tool_execution_start`                           | `tool_call_started`, named `Bash`, `Read`, `Edit`, `Write`, `Grep`, `Glob`, with `file_path`                   |
| `tool_execution_end`                             | `tool_call_finished`, then `file_changed` for a successful `edit` or `write`                                   |
| `compaction_start` / `compaction_end`            | `compaction_updated` running, done or failed                                                                   |
| `message_end` (assistant)                        | usage and the last error of the turn                                                                           |
| `agent_settled`                                  | `turn_completed` with usage, cost and context window, `turn_failed` for an error stop, or the interrupted turn |
| `extension_ui_request` `hinacode:approve`        | answered from the access mode, or `approval_requested`                                                         |
| other `select`, `confirm`, `input`, `editor`     | `question_requested`, answered with `extension_ui_response`                                                    |

`agent_end` does not end the turn: pi may still retry, compact or run queued steering. Only `agent_settled` does.

**Steer and interrupt.** `steer` sends pi's `steer` command, which pi delivers after the current tool calls finish. Stop sends `clear_queue` and `abort`, then waits up to five seconds for `agent_settled` before it kills the process. Open tool calls close as interrupted.

**Models and commands.** A probe process answers `get_available_models` (cached ten minutes) and `get_commands` for a folder (cached one minute). A model's effort levels follow pi's own rule: none without `reasoning`, otherwise `off` to `high`, plus `xhigh` and `max` when its `thinkingLevelMap` names them, minus levels it maps to `null`. `run_agent` gives pi only picked models, as for opencode, because pi lists every model of every provider it knows.

## Out of scope

- Signing in to pi's providers from HinaCode. `pi auth login` stays in the terminal.
- Session import, fork from a turn, the usage panel and plan limits. pi has the data (`fork`, session JSONL with per message usage), and each is its own pull request.
- Sub-agents and background tasks. pi has neither built in.
- An auto-compaction threshold. pi compacts by its own `compaction` settings and takes no per-process threshold, so the setting stays hidden for pi.

## Verification

- `pi/events.test.ts` maps a stream recorded from pi 1.5.2. `pi/extension.test.ts` runs the extension against a stub `pi` API.
- `pi/index.integration.test.ts` runs a fake `pi --mode rpc` over stdio through a turn with tool calls, approvals in each access mode, a question, steer, interrupt, resume, a lost session and an error stop.
- With `verify-hinacode` and the real `pi` binary: pick a pi model, send a prompt in Supervised that writes a file, allow it, and check the file and the reply.
