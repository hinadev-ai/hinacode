# magpie

Status: Building
Date: 2026-11-07

## Problem

[magpie](https://github.com/yetone/magpie) is a local model gateway. A developer who runs it has DeepSeek, Kimi, GLM, OpenRouter models, extra subscriptions and routing groups behind one URL, and runs Claude Code on any of them with `claude-magpie`. HinaCode cannot run a thread that way. Pointing Claude Code's own `settings.json` at magpie moves every Claude Code session on the machine instead of one thread.

## User flow

1. The developer runs the magpie app or `magpie serve`.
2. The model picker has a magpie tab with magpie's mark, next to Claude Code, Codex, Muse Code and opencode. It lists every model magpie serves. When two share a name, such as Claude Haiku 5.5 from `anthropic` and from `claude`, each row names its magpie provider.
3. A magpie thread works like a Claude Code thread: streaming, tools, approvals, steering, sub-agents, background tasks, compaction and fork. Its replies come from the model picked in the magpie tab.
4. Picking another magpie model keeps the session. Moving the thread to Claude Code or another agent is an agent switch, so it starts a new session there.
5. The effort control offers the levels magpie reports that Claude Code can send.
6. When magpie is not running, the magpie tab is not there, account settings say "magpie is not running", and a magpie thread fails its turn with the same message.

## Design

- magpie has no agent loop of its own. It runs an existing agent through its gateway, either Claude Code with `--settings <magpie>/claude-launch/settings.json` (`magpie claude run`, installed as `claude-magpie`) or `opencode acp` with its provider only (the Magpie agent it adds to JetBrains Air). HinaCode follows the first form, because the Claude harness maps every capability in `docs/agent-providers.md` and the ACP one maps few.
- `ProviderId` gains `magpie`. Migration `0044_magpie_provider` widens the `provider` CHECK on `thread` and `automation`.
- The Claude provider's session handling is `makeClaudeHarness({ id, listModels, launchEnv })` in `src/main/agents/claude/index.ts`. `ClaudeProvider` and `MagpieProvider` are two instances, each with its own sessions, wakes, sub-agents and background tasks. `ClaudeProvider` adds the account, plan limits, session copy and session import, which read Claude's home.
- `launchEnv(model)` returns the variables a session's Claude Code process starts with. The harness passes them in the SDK's `settings`, the `--settings` layer that wins over the user's `settings.json` and the shell, as `claude-magpie` relies on. A session whose launch variables differ from the next turn's resumes in a new process. Claude's are always empty, so its model changes still use `setModel`.
- `src/main/agents/magpie/gateway.ts` finds the gateway the way magpie's [integration guide](https://github.com/yetone/magpie/blob/main/docs/integrating.md) asks. It reads `port` from `$XDG_CONFIG_HOME/magpie/settings.json` or `~/.config/magpie/settings.json`, falls back to 3425, and never writes the file. `GET /api/hello` must answer `name: "magpie"`. Models come from `GET /v1/models` on every list. A schema decodes both. Every request, the turn's included, sends the key `magpie-hinacode`, so magpie counts HinaCode by name.
- A magpie turn's variables point Claude Code at the gateway with that key, pin every model tier and the sub-agent model to the thread's model, declare the model's effort levels in `CLAUDE_CODE_MODEL_CAPABILITIES`, and blank `ANTHROPIC_API_KEY` and the cloud switches that would route around the gateway. These are the variables magpie writes into its own launch file.
- The account is the gateway, external while it answers and signed out otherwise. Signed out hides the tab, the same rule every agent follows.
- `providerInfo.magpie.subagentModels` is `picked`, as for opencode. A gateway lists models the account may not reach, and `run_agent` would otherwise list all of them in every agent's instructions.
- The gateway listens on loopback and takes any key from this machine, so HinaCode stores no secret for it.

## Out of scope

- Plan limits. magpie's `GET /v1/magpie/quotas` could feed them in a follow-up.
- Session import and account switching. Claude Code threads already import the same transcripts.
- Starting magpie, adding providers or editing routing groups from HinaCode. magpie's app does that.

## Verification

- `src/main/agents/magpie/gateway.integration.test.ts` runs a real HTTP server as the gateway: the port from `settings.json`, the key on every request, a server that is not magpie, nothing listening, and a malformed model list. `gateway.test.ts` covers model mapping, shared labels and the launch variables.
- `src/main/agents/claude/index.test.ts` runs `MagpieProvider` against the faked SDK: its models and account, the gateway in the flag settings, a resume in a new process on a model change, and the error when magpie is not running.
- In the real app with magpie running, a magpie thread answers, and magpie's request log at `GET /v1/magpie/usage/requests` lists the session's calls under `hinacode` on the picked model, side requests included. Picking another magpie model continues the same session.
