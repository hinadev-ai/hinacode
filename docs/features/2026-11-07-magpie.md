# magpie models in Claude Code threads

Status: Building
Date: 2026-11-07

## Problem

[magpie](https://github.com/yetone/magpie) is a local model gateway. A developer who runs it has DeepSeek, Kimi, GLM, OpenRouter models, extra subscriptions and routing groups behind one URL. HinaCode's Claude Code threads only see Anthropic's models. To use the rest, the developer points Claude Code's own `settings.json` at magpie, which moves every Claude Code session on the machine at once instead of one thread.

## User flow

1. The developer runs the magpie app or `magpie serve`.
2. A Claude Code thread's model picker lists magpie's models under a magpie heading, after Claude Code's own. Each row shows the model name and the magpie provider it comes from, such as Kimi K3 from `opencode-go`.
3. Picking one switches the thread. The next turn runs Claude Code through the gateway on that model, with the same session, worktree, approvals and tools. Picking a Claude Code model again switches back, and the session continues.
4. The effort control offers the levels magpie reports for the model, minus any Claude Code cannot send.
5. When magpie is not running, the magpie section is not there. A thread still set to a magpie model fails its turn with "magpie is not running".

## Design

- magpie is a model source, not an agent, so it gets no `ProviderId`. A thread on a magpie model is a Claude Code thread. One session then survives model changes, where a separate agent would drop the session on every switch.
- A magpie model's id is `magpie/<gateway id>`, such as `magpie/opencode-go/kimi-k3` or `magpie/group/daily`. `thread.model` stores that string, so nothing in the schema or migrations changes. `src/shared/magpie.ts` owns the prefix.
- `src/main/agents/magpie.ts` finds the gateway the way magpie's [integration guide](https://github.com/yetone/magpie/blob/main/docs/integrating.md) asks. It reads `port` from `$XDG_CONFIG_HOME/magpie/settings.json` or `~/.config/magpie/settings.json`, falls back to 3425, and never writes the file. `GET /api/hello` must answer `name: "magpie"`.
- Models come from `GET /v1/models` on every list, so a provider the user adds in magpie shows up on the next one. A schema decodes both responses. HinaCode's own calls send the key `magpie-hinacode`, and magpie counts them under HinaCode. magpie counts a turn's calls under Claude Code, which it recognizes by User-Agent.
- The Claude provider appends magpie's models to its own. A turn on a magpie model starts Claude Code with `ANTHROPIC_BASE_URL` at the gateway, `ANTHROPIC_AUTH_TOKEN` set to the HinaCode key, and the model pinned for every tier in `ANTHROPIC_DEFAULT_*_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL`. magpie's own Claude Code adapter writes the same variables. Without the pins, Claude Code's side requests and sub-agents ask the gateway for a Claude model the user may not have.
- Claude Code applies the `env` of the user's `settings.json` over the process env. A user who already connected Claude Code to magpie keeps their own tier pins, which name magpie models too. The auth token wins over a claude.ai login, so a routed session has no claude.ai connectors.
- Those variables are fixed per process. A change of model into, out of, or between magpie models restarts the warm session with `resume`. A change between Claude Code models still calls `setModel` on the live session.
- The gateway listens on loopback and takes any key from this machine, so HinaCode stores no secret for it.

## Out of scope

- Codex and opencode threads. Codex takes a model provider per thread through `thread/start` config, but ignores config on `thread/resume` for a loaded thread. Switching sources mid-thread there needs its own design.
- Starting magpie, adding providers or editing routing groups from HinaCode. magpie's app does that.
- A row for HinaCode on magpie's Agents page. That is an adapter in magpie's repository.

## Verification

- `src/main/agents/magpie.integration.test.ts` runs a real HTTP server as the gateway. It covers the port from `settings.json`, the key on every request, a server that is not magpie, nothing listening, and a malformed model list. `magpie.test.ts` covers the model mapping and the launch env.
- In the real app with magpie running, a Claude Code thread on a magpie model answers, and magpie's request log at `GET /v1/magpie/usage/requests` lists the turn's session on that model. Switching the thread back to a Claude Code model continues the same session.
