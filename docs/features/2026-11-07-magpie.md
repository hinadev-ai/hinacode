# magpie

Status: Building
Date: 2026-11-07

## Problem

[magpie](https://github.com/yetone/magpie) is a local model gateway. A developer who runs it has DeepSeek, Kimi, GLM, OpenRouter models, extra subscriptions and routing groups behind one URL, and runs Claude Code on any of them with `claude-magpie`. HinaCode cannot run a thread that way. Pointing Claude Code's own `settings.json` at magpie moves every Claude Code session on the machine instead of one thread.

## User flow

1. The developer runs the magpie app or `magpie serve`.
2. The model picker has a magpie tab with magpie's mark, next to Claude Code, Codex, Muse Code and opencode. It lists every model magpie serves. When two share a name, such as Claude Haiku 5.5 from `anthropic` and from `claude`, each row names its magpie provider.
3. A magpie thread works like a Claude Code thread: streaming, tools, approvals, steering, sub-agents, background tasks, compaction and fork. Its replies come from the model picked in the magpie tab.
4. Picking another magpie model keeps the session. Moving the thread to Claude Code or another agent is an agent switch, so it starts a new session there.
5. The effort control offers the levels magpie reports that Claude Code can send. The Fast toggle shows on a model magpie serves in a fast tier, such as Opus on an Anthropic key or GPT-6.1-Sol on a ChatGPT plan, and runs the thread's turns there.
6. To use magpie on another machine, the developer turns on Share on local network there, adds a gateway key, and enters the gateway's address and key under Settings, Providers, magpie. Test reports the magpie version and how many models it serves, or why it could not connect: nothing answered, the key was refused, or the server is not magpie. Save keeps them, and the magpie tab lists that gateway's models.
7. When magpie is not running, the magpie tab is not there, account settings say "magpie is not running", and a magpie thread fails its turn with the same message.

## Design

- magpie has no agent loop of its own. It runs an existing agent through its gateway, either Claude Code with `--settings <magpie>/claude-launch/settings.json` (`magpie claude run`, installed as `claude-magpie`) or `opencode acp` with its provider only (the Magpie agent it adds to JetBrains Air). HinaCode follows the first form, because the Claude harness maps every capability in `docs/agent-providers.md` and the ACP one maps few.
- `ProviderId` gains `magpie`. Migration `0044_magpie_provider` widens the `provider` CHECK on `thread` and `automation`.
- The Claude provider's session handling is `makeClaudeHarness({ id, listModels, launchEnv })` in `src/main/agents/claude/index.ts`. `ClaudeProvider` and `MagpieProvider` are two instances, each with its own sessions, wakes, sub-agents and background tasks. `ClaudeProvider` adds the account, plan limits, session copy and session import, which read Claude's home.
- `launchEnv(model)` returns the variables a session's Claude Code process starts with. The harness passes them in the SDK's `settings`, the `--settings` layer that wins over the user's `settings.json` and the shell, as `claude-magpie` relies on. A session whose launch variables differ from the next turn's resumes in a new process. Claude's are always empty, so its model changes still use `setModel`.
- `src/main/agents/magpie/gateway.ts` finds the gateway the way magpie's [integration guide](https://github.com/yetone/magpie/blob/main/docs/integrating.md) asks. It reads `port` from `$XDG_CONFIG_HOME/magpie/settings.json` or `~/.config/magpie/settings.json`, falls back to 3425, and never writes the file. `GET /api/hello` must answer `name: "magpie"`. Models come from `GET /v1/models` on every list. A schema decodes both. Every request, the turn's included, sends the key `magpie-hinacode`, so magpie counts HinaCode by name.
- A magpie turn's variables point Claude Code at the gateway with that key, pin every model tier and the sub-agent model to the thread's model, declare the model's effort levels in `CLAUDE_CODE_MODEL_CAPABILITIES`, and blank `ANTHROPIC_API_KEY` and the cloud switches that would route around the gateway. These are the variables magpie writes into its own launch file.
- A model has fast mode when its `service_tiers` in `/v1/models` include `priority`, the field magpie's other clients read for their Fast switch. Claude Code refuses fast mode through a gateway and through the Agent SDK, even with `fast_mode` in `CLAUDE_CODE_MODEL_CAPABILITIES`. So a fast thread's launch variables set `CLAUDE_CODE_EXTRA_BODY` to `{"speed":"fast"}`, which Claude Code merges into every request body. magpie reads `speed: "fast"` as Claude's fast mode and sends the vendor's priority tier, which its request log records as `tier_sent`. Toggling Fast changes the launch variables, so the session resumes in a new process. `speed` is added only when the model lists the tier. magpie passes `speed` on as it is to a vendor without one, and Anthropic refuses it with a 400 on a model without fast mode, such as Haiku. So every magpie turn sets the variable: it keeps the other fields of an inherited `CLAUDE_CODE_EXTRA_BODY` and drops its `speed`, and it overrides the value in Claude Code's own `settings.json`, whose other fields a magpie turn does not get.
- `Settings.magpieEndpoint` holds the address of a gateway on another machine, null for the local one. Its key is the secret `magpie.key`, sealed by the keyring like every secret and never sent to the renderer. The secret stores the key with the origin it was saved for, and HinaCode sends it only to that origin, so a lookup that runs between saving a new address and its key never carries the old key to the new address. The rpc `magpie.saveKey` binds a typed key to the typed address, and drops the stored key when the address moves to another origin without one. Every request and every turn's `ANTHROPIC_AUTH_TOKEN` carry that key, and `magpie-hinacode` without one. A shared magpie keeps `/api/hello` behind its web sign-in, so a remote endpoint skips that check and `/v1/models` is the connection check: a 401 there is reported as a refused key, and a body that is not a model list as unreadable. The rpc `magpie.test` takes the typed address and key, falling back to the saved key, and runs the same check plus a model list, so Test proves what Save would use.
- The account is the gateway, external while it answers and signed out otherwise. Signed out hides the tab, the same rule every agent follows.
- `providerInfo.magpie.subagentModels` is `picked`, as for opencode. A gateway lists models the account may not reach, and `run_agent` would otherwise list all of them in every agent's instructions.
- The gateway listens on loopback and takes any key from this machine, so HinaCode stores no secret for it.

## Out of scope

- Plan limits. magpie's `GET /v1/magpie/quotas` could feed them in a follow-up.
- Session import and account switching. Claude Code threads already import the same transcripts.
- Starting magpie, adding providers or editing routing groups from HinaCode. magpie's app does that.

## Verification

- `src/main/agents/magpie/gateway.integration.test.ts` runs real HTTP servers as gateways: the port from `settings.json`, the key on every request, a saved endpoint with its key, a refused key, an address where nothing answers, a server that is not magpie, and a malformed model list. `gateway.test.ts` covers model mapping, shared labels and the launch variables.
- `src/main/agents/claude/index.test.ts` runs `MagpieProvider` against the faked SDK: its models and account, the gateway in the flag settings, a resume in a new process on a model change and on turning fast mode on, and the error when magpie is not running.
- `src/main/agents/magpie/index.integration.test.ts` runs the provider, the SDK and the real Claude Code against a fake gateway and reads every request body: `speed: "fast"` on each request of a fast turn, none after Fast is off, none on a model without the tier, and a turn on a saved endpoint carrying the saved key. The two turns need `claude` on the `PATH` and are skipped without it.
- In the real app with magpie running, a magpie thread answers, and magpie's request log at `GET /v1/magpie/usage/requests` lists the session's calls under `hinacode` on the picked model, side requests included. Picking another magpie model continues the same session. A turn on GPT-6.1-Sol with Fast on shows `tier_sent: priority` in that log, and none after Fast is turned off.

`Settings.providerEnabled` turns each agent on or off in Settings > Models. A disabled agent leaves the model picker tabs (unless the thread already uses it), the automation form and the starting provider of new threads. Existing threads keep running.
