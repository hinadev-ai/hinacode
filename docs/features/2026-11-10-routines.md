# Routines

Status: Building
Date: 2026-11-10

## Problem

Automations started threads from five triggers: a webhook, pull request events, and pollers for GitHub issues, Linear issues and Slack mentions. The pollers carried most of the code and most of the failure modes (tokens, cursors, rate limits, one error row per minute), and the agent can already reach Linear and GitHub itself through MCP and `gh`. What developers kept asking for was simpler: "run this prompt every weekday at 9" and "let my CI start this prompt". Neither was possible, because nothing ran on a clock.

## User flow

1. Settings > Routines lists every routine on every machine this HinaCode reaches, grouped by machine. Each row shows the name, the schedule in words, the next run, the last run and an enable switch.
2. New routine opens a form: name, project, schedule, prompt, agent (provider, model, effort) and workspace (local or a new worktree). The project picker decides the machine, because a routine runs where its project lives.
3. The prompt field is the thread composer's editor, so `/` lists the project's skills and commands, and `@` mentions files.
4. The schedule is a preset (every hour, every day, weekdays, every week) with a time, or a custom cron expression. The form shows the next three run times in the machine's time zone. A routine can have no schedule and run only from its webhook or Run now.
5. Each routine has a webhook URL. A caller authenticates with the machine's webhook secret, either `Authorization: Bearer <secret>` or a GitHub style `X-Hub-Signature-256` HMAC of the body. A non-empty body is appended to the prompt as a fenced block.
6. Run now starts a thread at once. Every run, from any source, lands in the run history with a link to its thread.
7. The CLI manages them too: `hinacode routines ls`, `run <id>`, `enable <id>` and `disable <id>`.

## Design

### Data

```ts
type RoutineSchedule = { cron: string; timezone: string }

type Routine = {
  id: string
  projectId: string
  name: string
  enabled: boolean
  prompt: string
  provider: ProviderId
  model: string
  effort: string | null
  workspace: "local" | "worktree"
  schedule: RoutineSchedule | null
  nextRunAt: Timestamp | null
  lastRun: RoutineRun | null
  createdAt: Timestamp
  updatedAt: Timestamp
}

type RoutineRun = {
  id: string
  routineId: string
  threadId: string | null
  source: "schedule" | "webhook" | "manual"
  status: "started" | "skipped" | "failed"
  error: string | null
  createdAt: Timestamp
}
```

- `nextRunAt` is stored, not derived, so a run that came due while the app was closed is visible on launch and fires once. It is null when the routine is disabled or has no schedule, which makes "a disabled routine with a pending run" unrepresentable.
- `schedule.cron` is checked by `isCronExpression` at the rpc boundary and in the form: it must parse against `schedule.timezone` and match at least once, because `Cron.parse` accepts `0 9 30 2 *` and `Cron.next` then throws.
- Migration `0047_routines` creates `routine` and `routine_run`, copies each automation's name, project, prompt, agent and workspace into a disabled routine with no schedule, and drops the automation tables. Pollers' cursors, trigger settings and run history do not carry over.
- `Settings.routines` holds the webhook listener's `bindHost` and `port`, replacing `Settings.automations`. Migration 0047 moves a stored `automations` value to `routines`, so a custom bind host or port survives. The secret lives in `Secrets` under `routines.webhookSecret`. It is created when the user presses Create secret, shown once, and can be rotated; until then the webhook answers 401.

### Limit

A machine holds at most 100 routines. `Routines.create` refuses the 101st with an error the form shows, so the limit covers the desktop, the CLI and `hinacode rpc` alike. It bounds the scheduler's fibers and the run history a careless script could create.

### Scheduler

`services/Scheduler.ts` is a small Effect service with two methods, `put(job)` and `remove(id)`. A job is `{ id, cron, nextRunAt, run }`. Each job gets a fiber in a `FiberMap`. The fiber sleeps until `nextRunAt`, at most a minute at a time measured against the wall clock, because timers don't count the time a laptop spends asleep. When due it calls `run(dueAt)` and moves on to `Cron.next(cron, now)`. A `nextRunAt` in the past fires once, then skips to the next future time, so a laptop opened at 10:00 runs the 9:00 routine once rather than replaying a night of hourly runs.

Effect's `Scheduler` module is the fiber task scheduler, not a job scheduler, so it is not used. `Cron` computes the times and the wall clock decides when to wake.

`Routines` owns the rows and hands each enabled, scheduled routine to the scheduler on startup, create, update and enable. Its `run` claims the slot with `UPDATE routine SET next_run_at = :next WHERE id = :id AND next_run_at = :due`. Only the update that changes a row starts a thread, so a crash or a duplicate fiber can't run the same slot twice.

A scheduled run is skipped, with a `skipped` row saying why, while the routine's previous thread is still running or waiting on a human. Webhook and manual runs always start.

When a scheduled run fails and the routine's last three scheduled runs, ignoring skipped ones, all failed, the routine pauses: `enabled` goes to 0, `nextRunAt` to null, and its job leaves the scheduler. The run event is the only push, and the list rereads on it.

### Starting a thread

A run creates a thread titled `<routine name> <first 5 characters of the run id>`, with `createdBy: "routine:<id>"` and the routine's provider, model and effort. The title names the worktree branch, so each run gets its own branch instead of colliding with the previous run's worktree. The prompt then goes through `AgentRunner.send` with the workspace choice, as the CLI's `run` does, and a worktree routine starts from the project's current branch.

Claiming the run, creating the thread and recording it are one uninterruptible step, so a webhook caller that hangs up or an edit that replaces the scheduler job can't leave a `started` run with no thread. `send`, which may wait on `git worktree add` and a setup script, is forked into the service's scope: the webhook answers as soon as the thread exists, quitting the app still stops it, and a failure marks the run `failed`.

### Keeping the inbox to one run per routine

When a run creates its thread, earlier runs of the same routine that are idle, unpinned, unsettled and have no reply beyond the routine's prompt are settled. The Inbox, its count and the dock badge then hold the newest run of each routine, and the older ones wait on the Settled shelf. A run you replied to, a run waiting on an approval or a usage limit, and a run that has not started its turn yet stay where they are. Settling goes through `Threads.settleIf`, not `Settle`, so it leaves terminals and ports alone.

The run history fetches the newest 200 runs and shows them 20 at a time.

### Webhook

One listener per machine, on `Settings.routines`, serves `POST /hooks/routines/:id`. It answers 401 without a valid secret, 404 for an unknown routine, 409 for a disabled one, and 202 with `{ runId, threadId }` otherwise. An `Idempotency-Key` or `X-GitHub-Delivery` header makes retries safe, through a unique index on `(routine_id, event_key)` for started runs.

### Machines

There is no central scheduler. Each machine's SQLite file holds its own routines, and its own scheduler and webhook listener run them, desktop and `hinacode serve` alike. `routines.list` uses the `all` route, so the desktop and the CLI merge every connected machine's routines. Every other method routes to the owner of the routine id, so editing a cloud's routine from the desktop edits it on the cloud.

## Out of scope

- Event triggers (pull requests, GitHub issues, Linear, Slack). An agent can read those through MCP and `gh`, and a scheduled routine can poll them in its prompt. The Linear MCP tools stay.
- Prompt templates with `{{...}}` placeholders. The webhook body is appended as context instead.
- Running a routine on a machine other than its project's, or moving it.
- Catching up more than one missed run.

## Verification

- `services/Scheduler.test.ts` runs jobs under `TestClock`: a due job fires once, a past `nextRunAt` fires once and skips the backlog, `remove` stops a job.
- `services/routines/Routines.integration.test.ts` runs against real SQLite: create, enable and disable move `nextRunAt`, a claimed slot runs once, an overlapping scheduled run is skipped, the webhook rejects a missing or wrong secret and accepts both auth styles, and the migration copies automations into disabled routines.
- With `verify-hinacode`: create a routine every minute with the mock agent, watch a thread start, disable it, call the webhook with `curl`, and screenshot the list and form into `.context/`.
