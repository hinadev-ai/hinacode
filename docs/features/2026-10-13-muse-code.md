# Muse Code threads

Status: Building
Date: 2026-10-13

## Problem

Meta shipped Muse Code, its terminal coding agent, with Muse Wonder (`muse-wonder-1.0`) and Muse Wonder Full (`muse-wonder-full-1.0`). Muse Wonder Full only runs inside Muse Code on the Power Usage and Maximum Usage plans; the pay-as-you-go Model API does not serve it. A developer who wants to try it next to Claude Code and Codex has to leave kkcode for a terminal, and loses the worktree per thread, the approval cards, the PR links and the status bar.

## User flow

1. The composer's agent picker lists Muse Code with the Meta logo, next to Claude Code and Codex. The model picker lists what the signed-in plan offers, newest first, such as Muse Wonder Full, and the effort picker shows each model's tiers.
2. A turn streams like the other agents: text, reasoning, tool rows (`bash` shows as a command, `read_file`, `write_file`, `edit_file`, `search`, `web_fetch` and `web_search` get the matching icons), approval cards, questions, Steer and Stop.
3. The access picker maps to Muse's approval modes. Muse's OS sandbox stays on, with network allowed:
   - Supervised: asks before commands and edits its rules don't cover.
   - Auto: runs freely in the sandbox, network included, and asks before writing outside the workspace.
   - Full access: never asks.
   A change applies to the running turn at once.
4. "Allow" approves the whole command the card shows. Muse splits a compound shell command into stages and asks per stage; kkcode answers every stage of the same approval with the user's one decision.
5. The status bar shows the thread's tokens per model, sub-agents and Muse's reminder agents included, and a Muse Code group with the 5-hour and weekly windows once a Muse turn has run.
6. Settings > Models lists Muse Code with its CLI login and a default model. It has no "Add account" button (see Out of scope).

## Design

- `ProviderId` gains `"muse"`. Migration `0011_muse_provider` swaps the `provider` column of `thread`, `automation` and `agent_account` the way `0006` did, so its CHECK accepts `muse` without cascading deletes.
- Settings: `defaultModel` and `defaultAccount` gain `muse`. `Settings.get` merges each stored object over its default, so a row saved before a key existed still decodes.
- `AccountProviderId` (`claude`, `codex`) types `accounts.create`, so an added Muse account is refused at the rpc boundary, and the settings page hides the button for it.
- `src/main/agents/muse/` implements `AgentProvider` with `@muse-code/sdk`. It uses `spawnMspConnection` and the raw `Connection`, not `MuseClient`: the facade keeps the one notification handler for itself and drops `usage/changed`, and it has no steer, interrupt, model or approval-mode calls.
  - One `muse serve --trust-workspace --sandbox-network enabled` per agent home, like Codex's app-server, with `experimentalApi` for `account/read` and the `sessionMcp` capability. A session stays loaded in the host that opened it (another host gets `sessionInUse`), so a thread's turns always go to its home's host.
  - A turn is `session/start` or `session/resume` with the kkcode MCP server in `config.mcpServers`, then `turn/start`. The kkcode instructions ride as a leading text part, with `displayText` set to the user's prompt. MSP has no developer-instructions field.
  - Approvals come from the `approval/request` server request, answered `{}` (a presentation receipt). The decision goes out as `approval/decide` with the choice whose `decision` matches: `approved`, `approvedForSession`, then `denied` or `abort`. Questions come from `userInput/request` and go back as `userInput/answer`.
  - Plan limits: `usage/changed` pushes `{ window, weekly }` after a model call. The provider keeps the latest per home. A fresh host has none, so the group appears after the first Muse turn.
  - Thread usage: `view/page` reads a session's durable events without loading it. `session/tokenUsage` carries the model and counts of each completion, and `subagent` and `reminderChild` items name child sessions to read the same way. Each session's sum is memoized with its cursor, so a refresh pages only new events.
- Renderer: one `providerLabel` map replaces five copies, `ProviderIcon` maps `muse` to `RiMetaFill`, and the access hints become per-agent records.

## Out of scope

- Added Muse accounts. Muse Code has no home variable like `CLAUDE_CONFIG_DIR`. Pointing `XDG_CONFIG_HOME` at an account home would also move the `gh` and `mise` config the agent's commands read.
- Skills in the composer. `skill/list` needs a loaded session, so `listCommands` returns nothing for now.
- Sub-agents in the Agents tab. Their tokens are counted, but `subagent` items are not turned into `subagent_updated` yet.
- A sandbox-off Full access. Sandbox posture is fixed per host, and moving a loaded session between hosts needs the first host to exit.

## Verification

- `muse/*.test.ts` cover the pure mappings: catalog to models, account state, plan limits, approval choices, questions, tool names and usage sums.
- `muse/index.integration.test.ts` runs the provider against the real `muse` binary and a loopback fake of Meta's endpoint, so it needs no login: a text turn, a two-stage approval, a denial, a question, Stop, and usage paged from child sessions. It skips when `muse` is not on PATH, which includes CI today.
- `Settings.integration.test.ts` stores a settings object missing a key and reads it back.
- With `verify-kkcode`: start a Muse Code thread on Muse Wonder Full, run a command that needs approval, check the tool rows, the status bar tokens and the plan limits group, and switch access mode mid-turn. Check both themes.
