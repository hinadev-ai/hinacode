# Integrated terminal

Status: Shipped
Date: 2026-10-12

## Problem

A developer glances at a thread and wants a shell where the agent works: run the tests the agent says pass, check `git status`, start a dev server. Today they switch to another terminal app and `cd` into the worktree by hand. With several threads in several worktrees, that is the step where they land in the wrong directory.

## User flow

1. In a thread, press `mod+j` (or click the terminal button in the thread header). A drawer opens under the transcript with a shell in the thread's worktree, or in the project root when the thread has no worktree. The shell has focus.
2. Typing goes to the shell. App shortcuts with a modifier still work while the terminal has focus, so `mod+j` hides the drawer and `mod+l` jumps to the composer.
3. `mod+shift+\`` (or `+` in the drawer header) opens another session. Each session is a tab; its close button kills the shell.
4. Dragging the drawer's top edge resizes it, and the shell reflows to the new size.
5. When the shell exits, its tab says so and keeps the output. Archiving or deleting the thread, or quitting the app, ends every session of that thread.

## Design

### Engine

The renderer uses [`@wterm/dom`](https://github.com/vercel-labs/wterm) with the [`@wterm/ghostty`](https://www.npmjs.com/package/@wterm/ghostty) core, both pinned at `0.5.4`. The core is libghostty's VT emulator compiled to WebAssembly (`ghostty-vt.wasm`, built from Ghostty source with a small patch that exposes cell and row access).

What exists today (October 2026):

| Option                                        | Renderer                        | Maintenance                                                                                                                          |
| --------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `ghostty-vt.wasm` from ghostty-org's `tip`    | none, VT parser and state       | Official, rolling `tip` release, no npm package, no versioned release with the wasm yet                                              |
| `ghostty-web` (coder)                         | canvas, xterm.js-shaped API     | Last stable `0.4.0` in December 2025, last prerelease June 2026; security fixes (paste sanitizing, OSC 8 links) open since September |
| `@wterm/dom` + `@wterm/ghostty` (vercel-labs) | DOM rows, native textarea input | Releases every few weeks, last on 2026-09-29                                                                                         |

The official artifact has no renderer, and building one (glyph atlas, selection, IME, scrollback viewport) is a project of its own. Between the two packages that wrap it, wterm is the maintained one, and its design fits hinacode:

- Colors are CSS custom properties (`--term-fg`, `--term-color-0` to `--term-color-15`), so the palette is our OKLCH tokens and follows light, dark and named themes with no JavaScript.
- The input is a real textarea named "Terminal", so screen readers, `verify-hinacode` and Playwright can find and type into it.
- It has `fit()`, `resize()` and a paused-rendering mode for hidden tabs.

The mitchellh post that says libghostty's wasm build beats xterm.js on IO, reflow and rendering could not be fetched (x.com returns 402 without a login), so this doc relies on our own numbers below instead.

### Main process

`src/main/services/Terminals.ts`, an Effect service, keeps sessions in memory. Nothing is persisted and there is no migration.

```ts
interface TerminalSession {
  id: string
  threadId: string
  cwd: string
  cols: number
  rows: number
  status: "running" | "exited"
  exitCode: number | null
}
```

- `open(threadId, cols, rows)` resolves the cwd through `makeActiveWorkspace` (the worktree, or the project root once it is gone), then spawns `$SHELL` (or `/bin/zsh`) as a login shell with `node-pty`.
- pty output is buffered per session and flushed as one `terminal.data` push every 16 ms, or sooner once 256 KB is waiting. A `cat` of a large file sends a few dozen IPC messages a second instead of one per read.
- On exit the session flips to `exited`, keeps its last size, and `terminal.exited {id, exitCode}` is pushed after the final data flush.
- The shell pid is registered with `Ports.registerAgentPid`, so a dev server started from the terminal shows up in the thread's ports panel. Without it, the ports scan treats hinacode's own descendants as not the user's.
- `closeThread(threadId)` kills every session of a thread. The `threads.archive`, `threads.delete` and `projects.delete` handlers call it before the worktree or the rows go away. The layer's finalizer kills every session when the runtime is disposed on quit.

rpc methods in `src/shared/contract.ts`:

| Method            | Request                    | Response            |
| ----------------- | -------------------------- | ------------------- |
| `terminal.open`   | `{ threadId, cols, rows }` | `TerminalSession`   |
| `terminal.write`  | `{ id, data }`             | void                |
| `terminal.resize` | `{ id, cols, rows }`       | void                |
| `terminal.close`  | `{ id }`                   | void                |
| `terminal.list`   | `{ threadId }`             | `TerminalSession[]` |

Pushes on the existing `event` channel: `terminal.data { id, data }` and `terminal.exited { id, exitCode }`. `cols` and `rows` are integers between 1 and 1000, checked by the schema. Writing to an unknown or exited session fails with `NotFoundError`.

Trust boundary: the renderer can already run anything through an agent, and the shell runs as the user in a directory the user imported. The rpc only lets the trusted top-level frame write to a session id it was given.

### node-pty and Electron

`node-pty@1.1.0` is a Node-API addon, so one binary loads in both Node (vitest) and Electron 44. It ships prebuilds for macOS and Windows and compiles with node-gyp on Linux. No `@electron/rebuild` step is needed. Two setup details:

- `pnpm-workspace.yaml` allows its install script (`allowBuilds: node-pty: true`).
- Its macOS `spawn-helper` prebuild ships without the executable bit, so every spawn fails with `posix_spawnp failed`. `scripts/node-pty-spawn-helper.mjs` runs as `postinstall` and sets it.

electron-vite leaves dependencies external in the main bundle, so `node-pty` loads from `node_modules` at runtime.

### Renderer

- `useTerminals` (`src/renderer/stores/terminals.ts`), a zustand store keyed by thread id: sessions, the active tab and whether the drawer is open. `terminal.data` pushes go straight to the mounted terminal through a listener map, not through React state, so streaming output never re-renders the tree.
- `TerminalDrawer` sits under `ThreadView` in the thread route: a 32 px header with one tab per session, `+`, and close per tab; the terminal fills the rest. A `ResizeObserver` on the host calls `fit()`, and the resulting size goes to `terminal.resize`. Clicking anywhere in the drawer focuses the terminal.
- Hidden tabs stay mounted with rendering paused, so switching back shows the latest output without a replay.
- Before a screen initializes, output retains only the newest 512 Ki characters, at most 1 MiB of UTF-16 text. This also bounds output from sessions that survive a renderer reload while their drawers remain closed. When older output is discarded, the screen shows a notice after replaying the retained text. Once initialized, the VT core bounds scrollback to a 4 MiB byte budget; retained rows depend on terminal width.
- Palette: `--terminal-*` tokens in `index.css`, OKLCH, one set for light and one for dark. Background and foreground are `--background` and `--foreground`, so named themes carry over.
- Commands: `terminal.toggle` (`mod+j`) and `terminal.new` (`mod+shift+\``). App chords reach the app from inside the terminal unless their command sets `when: "!terminalFocus"`, in which case the shell gets them. See `docs/arch.md`, Keybindings.

## Out of scope

- Persisting sessions or scrollback across restarts. A restart ends the shell anyway.
- Split panes, renaming tabs, search UI, and links in output. wterm supports search and OSC 8; they can come later.
- Running a terminal outside a thread (home or settings).
- A separate IPC channel for terminal data. The benchmark below shows whether the shared `event` channel is the bottleneck.

## Benchmark plan

A throwaway Vite page in `.context/bench/` runs inside Electron 44 and drives three engines with the same input: `@xterm/xterm` (DOM renderer default, plus its WebGL addon), `ghostty-web`, and `@wterm/dom` with `@wterm/ghostty`.

1. Write throughput in MB/s: a 50 MB file of colored log lines (SGR colors on every line), and a 50 MB `yes`-style stream, written in 64 KB chunks, timed until the engine has parsed and painted the last chunk.
2. Reflow: 10,000 lines of scrollback at 120 columns, then resize to 80 columns, timed to the next painted frame.
3. Frame time while streaming at full speed: `requestAnimationFrame` deltas over the run, reported as p50, p95 and max.
4. Memory after 10,000 lines: `performance.memory.usedJSHeapSize` plus the wasm memory buffer size.
5. End to end through hinacode's IPC path: `terminal.open`, then `cat` of the 50 MB file in the shell, measuring bytes received by the renderer per second, IPC messages per second, and the time until the drawer shows the final line.

## Results

Apple M4 Pro, macOS 26.5, Electron 44.7, a 120 Hz display (8.3 ms frames). The machine was shared with other agent runs (load average 20 to 30), so absolute numbers are noisy; each figure is the median of three to six runs, and the engine ranking held in every run. node-pty alone swung the most (60 to 176 MB/s). Versions: `@xterm/xterm` 6.0.0 with `@xterm/addon-webgl` 0.19.0, `ghostty-web` 0.4.0-next.20, `@wterm/dom` and `@wterm/ghostty` 0.5.4.

Engines on their own, fed 64 KB chunks from memory:

| Engine             | Colored log (MB/s) | `yes` (MB/s) | Reflow 120 to 80 cols, 10k lines (ms to frame) | Frame p95 / max while streaming (ms) | JS heap / process memory after 10k lines (MB) |
| ------------------ | ------------------ | ------------ | ---------------------------------------------- | ------------------------------------ | --------------------------------------------- |
| xterm.js DOM       | 72.5               | 17.1         | 19.8                                           | 9.3 / 25.0                           | 23.2 / 54.0                                   |
| xterm.js WebGL     | **84.3**           | 17.7         | 21.0                                           | 9.3 / 24.1                           | 24.5 / 56.1                                   |
| ghostty-web        | 26.1               | 28.3         | **8.3**                                        | 9.3 / 9.4                            | **4.0** / 33.0                                |
| wterm (libghostty) | 30.5               | **50.8**     | 11.2                                           | 9.3 / 9.4                            | 4.9 / **24.3**                                |

End to end in hinacode, `cat` of the same files in a login shell, node-pty to the drawer:

| Path                              | Colored log (MB/s) | `yes` (MB/s) | IPC messages/s | Avg message | Frame p50 / p95 (ms)                     |
| --------------------------------- | ------------------ | ------------ | -------------- | ----------- | ---------------------------------------- |
| node-pty alone, no IPC (ceiling)  | 150                | 104          |                |             |                                          |
| pty to renderer, screen not shown | 46.0               | 58.4         | 187 to 235     | 254 KB      | 8.3 / 9.9                                |
| pty to visible drawer             | 39.6               | 55.5         | 160 to 225     | 254 KB      | 41.4 / 108.7 (color), 8.4 / 17.0 (`yes`) |

What this says:

- libghostty loses on colored output. xterm.js parses and paints SGR-heavy logs 2.4 to 2.8 times faster than either libghostty wrapper. A test runner or build log full of colors renders slower in hinacode than it would with xterm.js.
- libghostty wins on plain streams (`yes`: 2.9 times xterm.js through wterm), on reflow (2 times faster to the next frame), and on memory (a fifth of the JS heap, half the process memory). Its frames stay flat in the isolated run, where xterm.js drops a few to 25 ms.
- In the app, colored output arrives in 256 KB batches and wterm needs about 100 ms per batch, so the drawer drops to roughly 10 frames a second during a big colored `cat`. Plain output stays at 60 fps or better. Smaller batches would trade throughput for smoother frames; we have not tuned that yet.
- The `event` channel is not the bottleneck for colored output; the engine is (46 MB/s through IPC, 39.6 MB/s on screen). For plain output, IPC is the cap: 58 MB/s through IPC against about 100 MB/s from node-pty alone, with the screen keeping up. We did not measure a dedicated channel. It would use the same `webContents.send` transport and clone the same 256 KB strings, so we keep the shared one until a measurement says otherwise.
- Batching works: a 50 MB `cat` sends about 200 messages a second, not one per pty read.

We chose wterm despite the colored-output loss: 40 MB/s is far above what a person reads, the memory and reflow wins matter with several drawers open across threads, and the CSS-variable palette and textarea input fit the app. If colored throughput turns out to matter in practice, the engine lives in `terminalScreens.ts` alone, so switching to xterm.js touches one file.

## Verification

- `Terminals.integration.test.ts` opens a session in a real temp git repo, writes `echo hi`, sees `hi` in the pushed data, resizes, closes, and checks that `closeThread` ends every session of a thread.
- In the real app (`verify-hinacode` patterns over CDP): open a thread, press `mod+j`, run `pwd` and `git status` in the worktree, open a second tab, resize the drawer, close a tab, and screenshot light and dark.
