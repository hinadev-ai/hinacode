# End-to-end encryption for remote sessions

Status: Building
Date: 2026-11-25

## Problem

A phone, the web app or another desktop drives a machine over one WebSocket. On the relay path Cloudflare terminates TLS, so Cloudflare, and anyone who controls HinaCode's Cloudflare account, can read every prompt, diff, file preview, terminal byte and browser frame. On the direct path the socket is plain `ws`, so anyone on the same network reads the same frames. The relay's D1 also stores every shown machine's pairing token in plaintext and hands it to any signed-in device ([ADR 0021](../adr/0021-the-relay-holds-each-machines-pairing.md)), so a D1 read or one stolen device credential opens every machine. A session on a machine is a shell as the developer, so the operator path can run code, not only read it.

Developers asked for the default path to be safe without setting up Tailscale.

## User flow

**Pairing by QR code or pairing URL.** Nothing changes for the developer. The QR code now carries the machine's public key, so the scan pins it, and the token in the code enrolls the phone's own key. Settings, Remote lists the phone under Devices, and the machine shows a notification that a device was paired.

**A machine the device learned through the relay.** The relay now hands out the machine's address and public key, never a token. The first time a device connects, the device shows "Approve this device on studio-mac. Code K7QF-2M9D" and the machine shows a notification and a request in Settings, Remote with the same code. The developer checks that both codes match, chooses **Approve** on the machine and **Codes match** on the device. Each side's tap protects a different thing: the machine's tap decides who gets in, and the device's tap confirms the relay handed out the real machine's key. On `hinacode serve` the request is printed to the log, and `hinacode devices approve K7QF-2M9D` approves it.

**Revoking.** Settings, Remote, Devices lists each device with when it was added and last seen. **Remove** ends its live sessions at once and refuses it from then on. A lost phone is removed here.

**Reset pairing** (the old Rotate token) gives the machine a new key and a new token and removes every device. Every client sees "studio-mac has a different key now" and must pair again. That is the recovery path when the machine's key may have leaked.

**After updating.** Pairings saved before this change have no key, so the client says "Pair studio-mac again: this pairing predates encryption." An app that predates this change gets "The desktop speaks remote protocol 2, this app speaks 1. Update the older one." from the machine, the message it already shows for a version mismatch.

**A key change.** When the machine answers with a key other than the pinned one on the relay, or on the only address the pairing has, the client stops and says the key changed, and that someone may be impersonating the machine if the developer did not reset its pairing. It never replaces the pinned key on its own. A mismatch on a direct LAN address while a relay is also known is treated as a stranger at that address, as today, and the client moves on to the relay.

## Design

### Keys

- **Host key.** Each machine has one X25519 key pair, generated with its pairing token and stored as the `remote.hostKey` secret next to `remote.token`. The desktop seals it with the login keychain. `hinacode serve` has no keyring, so its key sits in the profile like its token does today ([`Secrets.ts`](../../src/main/services/Secrets.ts)). The first start after this change generates the key and a new token together, because the old token may already be in D1.
- **Device key.** Each client install has one X25519 key pair, used with every machine: the desktop in `remote.deviceKey`, the phone in `expo-secure-store`, the web app in `localStorage`. The web app's key is as safe as its origin; script on that origin could already read the token it used before.
- **Device registry.** The machine keeps the devices it trusts in a `remote_device` table: public key, name, added at, last seen at. A device is added by a valid pairing token or by the developer's approval. Pending requests live only in memory while their socket is open, at most 8 at a time, so a stranger who knows the public key and the hostname can ask, not fill the database.

### Pairing URL

`hinacode://connect?relay=…&host=…&port=…&token=…&key=<base64url public key>`. `parsePairingUrl` refuses a URL without `key`. `token` is optional, since a machine from the relay has none. A relay machine is `{ hosts, port, relay, key }`.

### Handshake

The client speaks first with `Noise_IK_25519_ChaChaPoly_SHA256` and the prologue `hinacode remote 2`. IK fits because the client always knows the host key, it takes one round trip, and the client's own key travels encrypted. The primitives are `@noble/curves`, `@noble/ciphers` and `@noble/hashes`, which run in Hermes, so the server, the desktop, the phone and the web app share one implementation (`src/shared/noise.ts`), checked against the published Noise test vectors.

1. On open the server sends a plaintext `challenge`, as before, for clients that predate this change. A new client ignores it.
2. The client sends handshake message 1 as a binary frame. Its encrypted payload is `{ name, token?, verify?, compactEvents? }`. Only the holder of the host key can read it.
3. The server answers with message 2. A message 1 that does not decrypt closes the socket with `4006`.
4. Every frame after that, both ways, is a binary frame: ChaCha20-Poly1305 over the JSON of a `ClientFrame` or `ServerFrame`, with its own key and counter per direction. A frame that fails to decrypt, arrives out of order, repeats, or arrives as text closes the socket. Nothing in the session is plaintext: calls, results, pushes, terminal output, file and image payloads, and remote browser frames all travel as these frames.
5. The server decides inside the channel. A trusted device key, or an unknown key with the right token, gets `ready`. Any other key, and any client that sent `verify`, gets `{ type: "pending" }`, appears in the approval list with the code, and gets `ready` once approved or closes with `4001` when denied, removed, or after 5 minutes.

The approval code is the first 40 bits of SHA-256 of the final handshake hash, in Crockford base32 as `XXXX-XXXX`. It is bound to this session, so someone in the middle would have to make two live handshakes produce the same 40 bits while the device waits, rather than search for a key pair offline.

Noise caps a transport message at 65,535 bytes. Frames reach 16 MiB, so after the handshake the same cipher states encrypt whole frames instead of Noise-sized chunks. The cipher allows that; it is the one place we leave the Noise framing.

`REMOTE_PROTOCOL_VERSION` becomes 2. The client sends no call before it has `ready`, and with `verify` set, before the developer chose **Codes match** too.

### Old clients and old pairings

There is no plaintext window. A machine answers a legacy `auth` that proves the token with a plaintext `ready` of version 2 and closes, so an old app shows its update message, and any other legacy `auth` closes with `4001`. A new client never sends a plaintext frame. A plaintext window would keep the token in every D1 backup working, which is the hole this change closes.

### Relay service

`PUT /v1/host/pairing` takes `{ hosts, port, key }` and `GET /v1/machines` returns it. The relay migration clears every stored pairing, so the tokens leave D1, and each machine publishes its new pairing at its next start. The relay page and its sign-in flow do not change.

### Surfaces

- `src/shared/noise.ts` and `src/shared/remote.ts`: the handshake, the frame cipher, the pairing URL, close codes.
- `src/main/remote/access.ts`, `server.ts`, `session.ts`: the host key, the registry, the handshake on the listener. Sessions send through a channel, so the CLI socket stays plaintext on its private Unix socket while the remote listener encrypts.
- rpc: `remote.devices` lists trusted and pending devices, `remote.devices.approve`, `remote.devices.deny` and `remote.devices.remove` act on them, and `remote.devices.changed` pushes changes. A trusted device may call them too, since it already has full access.
- Clients: `src/shared/transport.ts` for the phone and the web app, `services/Environments.ts` for the desktop. Each stores its device key, pins the host key and shows the approval code.
- Settings, Remote gains the Devices list with pending requests. The phone, the web app and the desktop's connection list show the approval code with **Codes match**.
- `hinacode devices`, `hinacode devices approve <code>` and `hinacode devices remove <name>` on a cloud.

### Threat model

| Who | Before | After |
| --- | --- | --- |
| Cloudflare, or whoever controls HinaCode's Cloudflare account | Reads and forges every relayed frame. | Sees ciphertext. Re-routing the tunnel reaches a server without the host key, and the client stops. |
| Relay operator, or anyone who reads D1 | Gets every shown machine's token and full access. | Gets addresses and public keys. A device key it signs in waits for the developer's approval on the machine. A host key it swaps in fails the code check on the device. |
| Someone on the LAN | Reads every direct frame and can take over a session. | Sees ciphertext. Answering at the machine's address without its key fails the handshake. |
| A stolen device credential for the relay | Lists every shown machine's token. | Lists addresses and public keys only. |
| A stolen, unlocked phone | Full access until the token is rotated. | Full access until the developer removes that device; other devices keep working. |
| Someone with the machine's host key | Not applicable. | Can impersonate the machine to clients. Reset pairing replaces the key. They already have the developer's files in practice. |

### What still leaks

Encryption hides content, not shape. Cloudflare and the relay still see which machine's hostname a client opens, when, from which IP, for how long, and the size and timing of each frame, so a large transcript load, a stream of small typing frames, or a screencast is recognisable by its pattern. D1 still holds each machine's name, its LAN and Tailscale addresses, and its public key. Someone on the LAN sees the same sizes and timings on the direct path. The WebSocket ping frames that keep the link alive are plaintext and empty. The app MCP server for outside apps ([ADR 0025](../adr/0025-a-second-mcp-server-for-outside-apps.md)) is served over the same tunnel as HTTPS to outside clients that cannot speak this handshake, so Cloudflare still terminates its TLS.

### Cost

Message-level compression no longer helps once frames are encrypted, so the listener turns `perMessageDeflate` off. The measured cost of the cipher on the phone and the desktop, and of the lost compression, is in the verification section.

## Out of scope

- Approving a device from the phone. A trusted device may call the approval methods, but only the desktop and the CLI show them for now.
- Compressing frames before encryption. It would win back bandwidth on slow networks but needs a padding decision first, so it waits for a measurement that asks for it.
- Hiding metadata: padding frames, cover traffic, or hiding which machine a client opens.
- Rotating the host key on its own. Reset pairing rotates the key and the token together.
- Encrypting the app MCP server, whose clients are outside apps.

## Verification

- `src/shared/noise.test.ts`: the published `Noise_IK_25519_ChaChaPoly_SHA256` vectors, a tampered, replayed or reordered frame closes the channel, and a 16 MiB frame round-trips.
- `src/main/remote/session.integration.test.ts` and the listener tests: a token enrolls a device, an unknown key waits and joins on approval, removing a device ends its session, a wrong host key closes with `4006`, a legacy client gets version 2, and every frame after message 1 is binary and decrypts only with the session keys.
- `src/shared/transport.test.ts`, `apps/mobile/src/lib/connection.test.ts`, `src/main/services/Environments.integration.test.ts`: pinned keys, the approval code, a key change stops the client, a key mismatch on a LAN address falls back to the relay.
- `relay/test/`: pairings carry no token, and the migration clears the old ones.
- `specs/RelayRouting.tla`: `TokenStaysWithMachine` still holds, and `CallsReachOnlyMachine` and `RelayCannotEnroll` hold with a relay that swaps keys and routes.
- By hand with `verify-hinacode`: two isolated instances, one paired to the other through a stand-in relay, approve with matching codes, run a thread, remove the device and watch the session end.
