# End-to-end encryption for remote sessions

Status: Building
Date: 2026-11-25

## Problem

A phone, the web app or another desktop drives a machine over one WebSocket. On the relay path Cloudflare terminates TLS, so Cloudflare, and anyone who controls HinaCode's Cloudflare account, can read every prompt, diff, file preview, terminal byte and browser frame. On the direct path the socket is plain `ws`, so anyone on the same network reads the same frames. The relay's D1 also stores every shown machine's pairing token in plaintext and hands it to any signed-in device ([ADR 0021](../adr/0021-the-relay-holds-each-machines-pairing.md)), so a D1 read or one stolen device credential opens every machine. A session on a machine is a shell as the developer, so the operator path can run code, not only read it.

Developers asked for the default path to be safe without setting up Tailscale.

## User flow

**Pairing by QR code or pairing URL.** Nothing changes for the developer. The QR code now carries the machine's public key, so the scan pins it, and a one-time secret in the code enrolls the phone's own key. The machine then shows a new QR code, lists the phone under Settings, Remote, Devices, and shows a notification that a device was paired.

**A machine the device learned through the relay.** The relay now hands out the machine's address and public key, never a secret. The first time a device connects, it shows "Enter K7Q-F2M on studio-mac, in Settings, Remote." The machine shows a notification that a device is waiting, and Settings, Remote has a field for the code. The developer types it there, then answers **Yes** on the device to "Did studio-mac accept the code?". Each step protects a different thing. Typing the code on the machine decides who gets in. The answer on the device confirms the relay handed out the real machine's key. On `hinacode serve` the request is printed to the log, and `hinacode devices approve K7Q-F2M` approves it.

**Removing a device.** Settings, Remote, Devices lists each device with when it was added and last seen. **Remove** ends its live sessions at once and refuses it from then on. A lost phone is removed here.

**Reset pairing** (the old Rotate token) gives the machine a new key and a new secret and removes every device. Every client sees that the machine no longer accepts it, and must pair again. That is the recovery path when the machine's key may have leaked.

**After updating.** Pairings saved before this change have no key, so the client says "Pair studio-mac again: this pairing predates encryption." An app that predates this change gets "The desktop speaks remote protocol 2, this app speaks 1. Update the older one." from the machine, the message it already shows for a version mismatch. An old app cannot read the new QR code at all, because the new code names its secret differently.

**A key change.** When a session to the pinned key fails on the relay, or on the only address the pairing has, the client stops and says "studio-mac did not accept this device. If you reset its pairing, pair again from its QR code." It never replaces the pinned key on its own, and relay sync never changes a stored key. A device that has only the relay to learn keys from, such as the web app, offers **Pair again**, which takes the relay's current key and goes through the code again. A failure on a direct LAN address while a relay is also known is treated as a stranger at that address, as today, and the client moves on to the relay.

## Design

### Keys and secrets

- **Host key.** Each machine has one X25519 key pair in the `remote.hostKey` secret. The desktop seals it with the login keychain. `hinacode serve` has no keyring, so its key sits in the profile like its token does today ([`Secrets.ts`](../../src/main/services/Secrets.ts)).
- **Pairing secret.** 32 random bytes in `remote.pairingSecret`, shown in the QR code as `secret`. It enrolls exactly one device: the machine replaces it as soon as a device enrolls with it, and when a device is removed. The client drops it once enrolled.
- **Device key.** Each client install has one X25519 key pair, used with every machine: the desktop in `remote.deviceKey`, the phone in `expo-secure-store`, the web app in `localStorage`.
- **Device registry.** The machine keeps the devices it trusts in a `remote_device` table: public key, name, added at, last seen at. Pending requests live only in memory while their socket is open. At most 8 wait at once, and a ninth evicts the oldest, so a stranger who knows the public key and the hostname can ask, not fill the database.
- **The old token.** `remote.token` stays only to answer clients that predate this change with the version message. It no longer opens anything.

### Pairing URL

`hinacode://connect?relay=…&host=…&port=…&key=<base64url public key>&secret=…`. `parsePairingUrl` refuses a URL without `key`, and `secret` is optional, since a machine from the relay has none. Keys are 32 bytes as unpadded base64url, 43 characters. A relay machine is `{ hosts, port, relay, key }`. Old apps require `token`, so they refuse the new URL instead of sending its secret in the clear.

### Handshake

The client speaks first with `Noise_IK_25519_ChaChaPoly_SHA256` and the prologue `hinacode remote 2`. IK fits because the client always knows the host key, and the client's own key travels encrypted. The primitives are `@noble/curves`, `@noble/ciphers` and `@noble/hashes`, which run in Hermes, so the server, the desktop, the phone and the web app share one implementation (`src/shared/noise.ts`), checked against the published Noise test vectors.

1. On open the server sends a plaintext `challenge`, as before, for clients that predate this change. A new client ignores it.
2. The client sends handshake message 1 as a binary frame, and the server answers with message 2. Both payloads are empty. A message 1 that does not decrypt closes the socket with `4006`.
3. Every frame after that, both ways, is a binary frame: ChaCha20-Poly1305 over the JSON of a `ClientFrame` or `ServerFrame`, with its own key and counter per direction. A frame that fails to decrypt, arrives out of order, repeats, or arrives as text closes the socket. Nothing in the session is plaintext: calls, results, pushes, terminal output, file and image payloads, and remote browser frames all travel as these frames.
4. The client's first frame is `hello { name, secret?, verify?, compactEvents? }`. The server acts on nothing before it, because message 1 can be replayed by anyone who recorded it, while `hello` decrypts only for the client that holds the session's ephemeral key.
5. A trusted device key, or an unknown key with the current secret, gets `ready`. Any other key, and any client that sent `verify`, waits for approval.

Until `ready`, the server reads frames of at most 1 KiB and only `hello`, `approval` and `ping`; anything else closes the socket. A pending request closes with `4001` when its code is never entered within 5 minutes, or the device is removed.

### Approval code

A code derived from the handshake alone can be searched: the party that speaks last can try ephemeral keys or payloads until its side shows the code the other side already shows. So the code mixes in a nonce from each side, committed before the other side reveals its own:

1. The server sends `pending { commitment }`, the SHA-256 of 32 random bytes `rM`.
2. The client sends `approval { nonce: rC }`.
3. The server sends `approval { nonce: rM }`, and the client checks it against the commitment.
4. Both show the first 30 bits of SHA-256(handshake hash, `rC`, `rM`) in Crockford base32, as `XXX-XXX`.

Someone in the middle has to commit on one side before learning the other side's nonce, so each attempt matches with probability 2^-30, and each attempt costs a request the developer sees.

The machine never shows a list of pending names with an Approve button. The developer types the code shown on the device, so a request the developer did not start cannot be approved by a careless tap, and a device's name, which the device chooses, appears only once it is trusted.

### Frames and limits

Noise caps a transport message at 65,535 bytes. Frames reach 16 MiB, so after the handshake the same cipher states encrypt whole frames instead of Noise-sized chunks. ChaCha20-Poly1305 allows that; it is the one place we leave the Noise framing.

`REMOTE_PROTOCOL_VERSION` becomes 2. The client sends no call before it has `ready`, and with `verify` set, before the developer answered **Yes** on the device.

### Old clients and old pairings

There is no plaintext window. A machine answers a legacy `auth` that proves the old token with a plaintext `ready` of version 2 and closes, so an old app shows its update message. Any other legacy `auth` closes with `4001`. A new client never sends a plaintext frame. A plaintext window would keep the token in every D1 backup working, which is the hole this change closes.

### Relay service

`PUT /v1/host/pairing` takes `{ hosts, port, key }` and refuses a body that still carries `token`, so a machine that has not updated cannot put one back. `GET /v1/machines` returns `{ hosts, port, key, relay }`. The relay migration clears every stored pairing, so the tokens leave D1, and each machine publishes its new pairing at its next start. The relay page and its sign-in flow do not change.

### Surfaces

- `src/shared/noise.ts` and `src/shared/remote.ts`: the handshake, the frame cipher, the approval code, the pairing URL, close codes.
- `src/main/remote/access.ts`, `server.ts`, `session.ts`: the host key, the secret, the registry, the handshake on the listener. Sessions send through a channel, so the CLI socket stays plaintext on its private Unix socket while the remote listener encrypts.
- rpc: `remote.devices` lists trusted devices and how many requests wait, `remote.devices.approve { code }` and `remote.devices.remove { key }` act on them, and `remote.devices.changed` pushes changes. The remote listener refuses all three, so a stolen phone cannot enroll a second key or keep itself from being removed. The desktop window and the CLI socket accept them.
- Clients: `src/shared/transport.ts` for the phone and the web app, `services/Environments.ts` for the desktop. Each stores its device key, pins the host key and shows the approval code.
- Settings, Remote gains the Devices list and the code field. The phone, the web app and the desktop's connection list show the approval code and the **Yes** confirmation.
- `hinacode devices`, `hinacode devices approve <code>` and `hinacode devices remove <name>` on a cloud.

### Threat model

| Who                                                           | Before                                                | After                                                                                                                                                      |
| ------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cloudflare, or whoever controls HinaCode's Cloudflare account | Reads and forges every relayed frame.                 | Sees ciphertext. Re-routing the tunnel reaches a server without the host key, and the client stops. It still serves the web app's JavaScript, see below.   |
| Relay operator, or anyone who reads D1                        | Gets every shown machine's token and full access.     | Gets addresses and public keys. A device key it signs in waits for a code the developer types on the machine. A host key it swaps in fails the code check. |
| Someone on the LAN                                            | Reads every direct frame and can take over a session. | Sees ciphertext. Answering at the machine's address without its key fails the handshake.                                                                   |
| A stolen device credential for the relay                      | Lists every shown machine's token.                    | Lists addresses and public keys only.                                                                                                                      |
| A stolen, unlocked phone                                      | Full access until the token is rotated.               | Full access until the developer removes that device. It cannot enroll another key, and its pairing secret was used up when it enrolled.                    |
| Someone with the machine's host key                           | Not applicable.                                       | Can impersonate the machine to clients. Reset pairing replaces the key. They already have the developer's files in practice.                               |

Three operator paths remain, and this change does not close them:

- **The web app's code.** The web app is served from HinaCode's Cloudflare account. Whoever controls that account can ship JavaScript that uses the browser's device key or reads its live sessions. A machine that has never trusted a web device is not exposed this way. The phone app and the desktop ship through their own updates.
- **Outside apps.** The app MCP server ([ADR 0025](../adr/0025-a-second-mcp-server-for-outside-apps.md)) can be approved on the relay page after signing in to the relay as the machine's owner, and its traffic is HTTPS that Cloudflare terminates, because its clients are outside apps that cannot speak this handshake. Approving outside apps only inside HinaCode is the follow-up that closes the first half.
- **Machines that have not updated.** Their token may still sit in old D1 backups and still opens them, until they update.

### What still leaks

Encryption hides content, not shape. Cloudflare and the relay still see which machine's hostname a client opens, when, from which IP, for how long, and the size and timing of each frame, so a large transcript load, a stream of small typing frames, or a screencast is recognisable by its pattern. D1 still holds each machine's name, its LAN and Tailscale addresses, and its public key. Someone on the LAN sees the same sizes and timings on the direct path. The WebSocket ping frames that keep the link alive are plaintext and empty. Close codes are plaintext, so someone on the path can close a session with any code, as they could always drop it.

### Cost

Frames used to compress on the wire with `perMessageDeflate`. Session JSON deflates about 3x (1 KiB frames 2.1x, 16 KiB to 2 MiB about 3.2x, measured on a real agent transcript), and ciphertext does not compress, so the listener turns `perMessageDeflate` off and the browser and desktop clients send about three times the bytes. Compressing before encrypting would win that back but makes frame sizes depend on content, which matters once an attacker can put text into a session, so it waits for a link where the bytes matter. The measured cost of the cipher is in the verification section.

## Out of scope

- Approving a device from the phone. The approval methods stay on the desktop window and the CLI.
- Compressing frames before encryption, see Cost.
- Hiding metadata: padding frames, cover traffic, or hiding which machine a client opens.
- Rotating the host key on its own. Reset pairing rotates the key and the secret together.
- Closing the web app and outside-app paths above.

## Verification

- `src/shared/noise.test.ts`: the published `Noise_IK_25519_ChaChaPoly_SHA256` vectors, a tampered, replayed or reordered frame closes the channel, and a 16 MiB frame round-trips.
- `src/main/remote/*.integration.test.ts`: a secret enrolls a device once and is replaced, an unknown key waits and joins when its code is entered, a replayed message 1 enrolls nothing, removing a device ends its session, a wrong host key closes with `4006`, a legacy client gets version 2, a frame over 1 KiB before `ready` closes the socket, and every frame after message 1 is binary.
- `src/shared/transport.test.ts`, `apps/mobile/src/lib/connection.test.ts`, `src/main/services/Environments.integration.test.ts`: pinned keys, the approval code, a key change stops the client, relay sync never changes a stored key, a failure on a LAN address falls back to the relay.
- `relay/test/`: pairings carry no token, a body with a token is refused, and the migration clears the old ones.
- `specs/RelayRouting.tla`: `TokenStaysWithMachine`, `CallsReachOnlyMachine` and `RelayCannotEnroll` hold with a relay that swaps keys and routes.
- By hand with `verify-hinacode`: two isolated instances, one paired to the other through relay sync, approve with the code, run a thread, remove the device and watch the session end.
- Cipher cost in Node: a handshake takes about 5 ms, and encrypting a frame on one end and decrypting it on the other runs at about 170 MB/s, so a 16 MiB frame costs about 100 ms in total. Hermes on a phone is not measured yet.
