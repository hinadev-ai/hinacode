# Tiny VM

Status: Building
Date: 2026-10-13

## Problem

An agent can edit code and run commands, but it cannot use a desktop. Checking a change in a real browser, driving a GUI program, or trying something risky needs a machine the agent can see and operate, that the developer can watch, and that the developer can take over for the parts an agent should not do, such as signing in.

The developer already runs [sbx](https://github.com/kjj6198/agent-sandbox/tree/main/sbx) on a Proxmox host. It restores Firecracker microVMs from a snapshot in about 40 ms, and each one has a 1280×800 desktop. hinacode has no way to give a thread one of them.

## User flow

1. Open Settings > Experimental and turn on Tiny VM. It is off by default. Once it is on, the page shows whether hinacode reaches the sbx host, for example "Connected to 192.168.1.10:7070. 0 of 64 sandboxes running."
2. In a thread, the activity bar gains a Tiny VM view. It stays hidden while the toggle is off, and so does its command in the palette.
3. With no VM, the view explains that the agent starts one when it needs a desktop, and offers Start VM.
4. The agent calls a `vm_*` tool. hinacode creates a sandbox for the thread, and the view shows its screen live and view-only, labelled "Agent has control".
5. Take control. The screen now takes the developer's mouse and keyboard, and the agent's pointer and keyboard tools wait. If one is waiting, the view says so in amber, because the agent needs the developer.
6. Hand back. A waiting tool skips its action and returns the current screen, telling the agent the screen may have changed.
7. Dragging files or folders onto the screen copies them into `~/Downloads` in the VM. The agent's next tool result names where they landed.
8. The other way, the agent calls `vm_pull_file` to hand back a file or folder the VM made or downloaded. It lands in a new folder on this machine and the agent copies it on from there.
9. The camera button saves the current screen as a PNG on this machine and reveals it in the file manager. It works whichever side has control.
10. Holding Stop VM for two seconds destroys the sandbox. Letting go early cancels it. Quitting hinacode destroys every thread's VM, and sbx destroys an idle one after its idle timeout (an hour by default). An open view does not count as use, so a forgotten panel cannot keep a VM alive.

## Design

### Settings

`Settings.experimental.tinyVm: boolean`, default `false`. Settings merges stored values over the defaults, so there is no migration.

`Settings.experimental.tinyVmTemplate: string`, default `"default"`, names the sbx template new VMs restore from. Settings lists the host's templates from `GET /v1/templates` (carried on `vm.host`) once the host answers. The start view can override the template for one VM through `vm.start`'s optional `template`. A running VM reports the template it was restored from in `ThreadVm`, and changing the setting leaves running VMs alone.

### Connection

hinacode uses the sbx CLI's login: `SBX_URL` and `SBX_TOKEN`, or else `<appData>/sbx/config.json`, which `sbx login` writes. The file is decoded with a schema. The token stays in main as `Redacted`, is never logged, and never reaches the renderer. Rotating it with `sbx login` updates hinacode too, so there is no second copy in `Secrets`.

### sbxd client

`services/tinyVm/sbx.ts` speaks the parts of the sbxd HTTP API hinacode needs:

- `POST /v1/sandboxes` with template `default`, plus `GET` and `DELETE /v1/sandboxes/{id}`.
- `POST /v1/sandboxes/{id}/exec`, decoding its frame stream (one type byte, a 4-byte big-endian length, the payload).
- `PUT` and `GET /v1/sandboxes/{id}/files?path=...`, moving uncompressed tar archives that hold one top-level entry. `services/tinyVm/tar.ts` writes plain ustar itself, because system tar on macOS adds AppleDouble entries the guest reader rejects. It reads ustar plus the pax headers Go's `archive/tar` writes in the guest for non-ASCII and long names. A `GET` stops reading once the archive passes its cap.
- `GET /v1/sandboxes/{id}/tcp?port=5900` with `Upgrade: tcp`, which becomes a raw TCP connection to the guest's Xvnc. The view adds `passive=1`, so watching is not activity for the idle timeout. An sbxd older than a459986 ignores it. The agent's input tunnel stays active.

### Agent input

The agent's pointer and keyboard go through the same VNC server the developer's view uses. `services/tinyVm/rfb.ts` is a minimal RFB 3.8 client: no security type, a shared session, and only `PointerEvent` and `KeyEvent` messages. Keys are X keysyms. xdotool names such as `Return` or `ctrl+l` map through a small table, and any other character maps to its Unicode keysym, which Xvnc adds to its keymap, so CJK text types too. Screenshots run `import -window root png:-` in the guest, since ImageMagick ships in the sbx templates. No guest packages are installed.

### State

`services/tinyVm/TinyVm.ts` keeps one VM per thread, in memory:

```
none ──start──▶ starting ──▶ running { control: agent | user, agentWaiting } ──stop──▶ none
                    └──────▶ failed { message } ──start──▶ starting
```

A `vm_*` tool or Start VM starts it, and concurrent starts share one creation. A 404 from sbxd means sbx expired the sandbox, so the state returns to `none`. Main pushes `vm.updated` on every change. Closing the last screen view while the developer has control hands it back, so an agent never waits on a view nobody has open.

### Screen

The view renders with noVNC's `RFB` class over an rpc-backed channel instead of a WebSocket:

1. `vm.screen.open` opens a tunnel in main and returns a stream id.
2. Main pushes `vm.screen.data`, batched every 16 ms like terminal output.
3. The renderer sends the developer's input with `vm.screen.send` and ends with `vm.screen.close`.

The token stays in main, no port opens, and the CSP is unchanged. The canvas is view-only unless the developer has control.

`vm.screenshot.save` runs the same guest screenshot the agent tools use and stages the PNG through `Attachments`, so the user's button and `vm_screenshot` with `save: true` store files the same way. The renderer reveals the staged path with `shell.reveal`. Guest passkey sign-in has its own design in `docs/features/2026-10-19-vm-passkey-relay.md`.

### MCP tools

`vm_screenshot`, `vm_click`, `vm_move`, `vm_drag`, `vm_scroll`, `vm_type`, `vm_key`, `vm_exec` and `vm_pull_file`:

- They are registered once and hidden with `McpSchema.EnabledWhen` while the toggle is off. That covers both `tools/list` and `tools/call`.
- Each starts the thread's VM on first use.
- The pointer and keyboard tools return a screenshot taken 500 ms after acting, which saves the agent a round trip per step.
- While the developer has control, those tools wait, and on hand back they return the current screen without acting.
- Files the developer dropped are named once, appended to the next pointer, keyboard or exec tool result.

### Persistent browser profile

Off by default behind `Settings.experimental.tinyVmProfile`. HinaCode keeps one gzip tar of the guest's `~/.config/chromium` next to its database (`<userData>/tiny-vm/chromium-profile.tgz`, mode 0600), with cache directories excluded. A new VM restores it before `vm.start` resolves, so no tool can launch Chromium ahead of it. The first running VM owns saving. Later VMs restore a copy and cannot save, which keeps two agents browsing as the same person from clobbering each other silently. Saving happens on Stop VM, on app quit within its bounded cleanup window, from the save button in the view (`vm.profile.save`), and every 10 minutes while the owner runs, because the host idle timeout can destroy a VM without asking. Saves run one at a time so they cannot overwrite an archive while another save reads it. A failed restore logs and starts fresh instead of failing the start.

Cookies and saved passwords are v10-encrypted by Chromium. Restoring them into a new sandbox works because every sandbox is a snapshot clone with the same machine identity, and because Chromium is launched with `--password-store=basic`, whose key derivation is not bound to a keyring. Verified live end to end (cookie, localStorage and saved password) before this was built. The stored tar still contains live sessions, and every thread's agent browses with them. That is the point of the feature, and why it is off by default.

### Guest helpers

The sbx template ships `xdotool`, `wmctrl`, `xclip`, `scrot`, tesseract and AT-SPI packages, plus two helpers: `sbx-windows` (windows, focus, pointer) and `sbx-ocr` (screen text). The agent instructions name them, so focus, window geometry and clipboard contents cost one `vm_exec` instead of a screenshot. They live in the sbx repo's template, built through the same API hinacode already speaks (`POST /v1/templates/{name}`).

### Dropped files

`vm.files.drop` carries host paths from the screen's drop handler to main, so file bytes never cross rpc. `TinyVm.dropFiles` tars each dropped file or folder (200 MB per drop, since archives are held in memory), makes `~/Downloads`, and PUTs each archive at it. The mkdir matters because the guest extractor renames the archive's top entry onto a missing destination instead of putting it inside. A drop is the developer's own action, so it works whichever side has control.

The credential that names the thread also names its VM, so an agent cannot reach another thread's machine.

### Pulled files

`vm_pull_file` copies a guest file or folder to `<userData>/tiny-vm/pulled/<threadId>/<uuid>/<name>` and returns that path. The guest is untrusted: anything that browses the web can be taken over, and the user has passwordless sudo, so it can send any bytes as the archive. The design keeps every decision about the host side in HinaCode:

- HinaCode picks the folder, a new one per pull. Neither the agent nor the guest chooses a host path, so the tool cannot write into the worktree, `.git/hooks` or `.claude`. Copying the result anywhere else is the agent's own action and goes through its permission mode.
- `writeTree` checks every entry before writing any: one top-level entry, and no empty, `.` or `..` segment, absolute path, backslash or NUL. It writes only files and folders, never symlinks or hard links, into a folder it just created, so no path can resolve outside it. Files open with `O_EXCL`, so a repeated entry cannot overwrite an earlier one.
- Files are written 0644 and folders 0755, whatever the archive says, so nothing arrives executable or setuid.
- A pull is held in memory, so it is capped at 200 MB, the same as a drop, and the read stops as soon as the archive passes it. Pax headers over 1 MiB are refused, as Go's reader does, so junk metadata cannot stall the main process.
- A truncated archive fails instead of passing for a whole one, and a failed write removes its folder.
- sbx answers 404 both for a destroyed sandbox and a missing guest path. On a 404 HinaCode asks for the sandbox, so a typo in the path does not forget a running VM.

No approval is asked. `vm_exec` can already print any guest file into the agent's context, and the copy lands where nothing runs it.

### Prompt

`agentInstructions({ tinyVm })` appends a `<tiny-vm>` block only when the toggle is on, and AgentRunner passes the result as `RunTurnInput.instructions`. Claude restarts its session, resuming the same conversation, when the instructions change. Codex and Muse Code receive them every turn.

### Transcript

Screenshots are not stored. AgentRunner drops image data from tool results before it publishes and persists them, and the tool row shows `[image]`.

## Out of scope

- Keeping a thread's VM across a hinacode restart. Sandboxes are disposable and boot in 60 ms, and quitting destroys them. Only the Chromium profile persists, and only with its toggle on.
- Copying the worktree into the VM, or reaching the developer's localhost from it. sbx sandboxes reach only the internet.
- Removing pulled files. They stay under `<userData>/tiny-vm/pulled` like staged attachments do.
- Showing pulled files in the transcript or the side panel.
- Other screen sizes and full Proxmox QEMU VMs.
- Screenshot thumbnails in the transcript.
- Showing the agent's pointer in the view. noVNC draws only the local cursor.

## Verification

Tests:

- `mcp/server.integration.test.ts` runs the tools against a fake sbxd and a fake VNC server. It checks that the tools are hidden while the toggle is off, that a screenshot comes back as an image, that a click becomes the right RFB events, and that a click waits while the developer has control.
- A test on the runner checks that the instructions carry `<tiny-vm>` only when the toggle is on.

In the real app, use `verify-hinacode` against the real sbx host:

1. Turn the toggle on and screenshot the connection status.
2. Drive the tools with `mcp-call.ts`, and screenshot the view while they act.
3. Take control and type into the VM, then check that a `vm_click` waits until hand back.
4. Run one short Claude turn that opens a page in the VM.
