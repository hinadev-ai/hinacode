# Tiny VM

Status: Building
Date: 2026-10-13

## Problem

An agent can edit code and run commands, but it cannot use a desktop. Checking a change in a real browser, driving a GUI program, or trying something risky needs a machine the agent can see and operate, that the developer can watch, and that the developer can take over for the parts an agent should not do, such as signing in.

The developer already runs [sbx](https://github.com/kjj6198/agent-sandbox-eval/tree/main/sbx) on a Proxmox host. It restores Firecracker microVMs from a snapshot in about 60 ms, and each one has a 1280×800 desktop. kkcode has no way to give a thread one of them.

## User flow

1. Open Settings > Experimental and turn on Tiny VM. It is off by default. Once it is on, the page shows whether kkcode reaches the sbx host, for example "Connected to 192.168.1.33:7070. 0 of 64 sandboxes running."
2. In a thread, the activity bar gains a Tiny VM view. It stays hidden while the toggle is off, and so does its command in the palette.
3. With no VM, the view explains that the agent starts one when it needs a desktop, and offers Start VM.
4. The agent calls a `vm_*` tool. kkcode creates a sandbox for the thread, and the view shows its screen live and view-only, labelled "Agent has control".
5. Take control. The screen now takes the developer's mouse and keyboard, and the agent's pointer and keyboard tools wait. If one is waiting, the view says so in amber, because the agent needs the developer.
6. Hand back. A waiting tool skips its action and returns the current screen, telling the agent the screen may have changed.
7. Stop VM destroys the sandbox. Quitting kkcode destroys every thread's VM, and sbx destroys an idle one after its idle timeout (an hour by default). An open view does not count as use, so a forgotten panel cannot keep a VM alive.

## Design

### Settings

`Settings.experimental.tinyVm: boolean`, default `false`. Settings merges stored values over the defaults, so there is no migration.

### Connection

kkcode uses the sbx CLI's login: `SBX_URL` and `SBX_TOKEN`, or else `<appData>/sbx/config.json`, which `sbx login` writes. The file is decoded with a schema. The token stays in main as `Redacted`, is never logged, and never reaches the renderer. Rotating it with `sbx login` updates kkcode too, so there is no second copy in `Secrets`.

### sbxd client

`services/tinyVm/sbx.ts` speaks the parts of the sbxd HTTP API kkcode needs:

- `POST /v1/sandboxes` with template `default`, plus `GET` and `DELETE /v1/sandboxes/{id}`.
- `POST /v1/sandboxes/{id}/exec`, decoding its frame stream (one type byte, a 4-byte big-endian length, the payload).
- `GET /v1/sandboxes/{id}/tcp?port=5900` with `Upgrade: tcp`, which becomes a raw TCP connection to the guest's Xvnc. The view adds `passive=1`, so watching is not activity for the idle timeout. An sbxd older than a459986 ignores it. The agent's input tunnel stays active.

### Agent input

The agent's pointer and keyboard go through the same VNC server the developer's view uses. `services/tinyVm/rfb.ts` is a minimal RFB 3.8 client: no security type, a shared session, and only `PointerEvent` and `KeyEvent` messages. Keys are X keysyms. xdotool names such as `Return` or `ctrl+l` map through a small table, and any other character maps to its Unicode keysym, which Xvnc adds to its keymap, so CJK text types too. Screenshots run `import -window root png:-` in the guest, since ImageMagick ships in the sbx templates. No guest packages are installed.

### State

`services/tinyVm/TinyVm.ts` keeps one VM per thread, in memory:

```
none ──start──▶ starting ──▶ running { control: agent | user, agentWaiting } ──stop──▶ none
                    └──────▶ failed { message } ──start──▶ starting
```

A `vm_*` tool or Start VM starts it, and concurrent starts share one creation. A 404 from sbxd means sbx expired the sandbox, so the state returns to `none`. Main pushes `vm.updated` on every change. Closing the last screen view while the developer has control hands it back, so an agent never waits on a view nobody has open.

### Screen

The view renders with noVNC's `RFB` class over an rpc-backed channel instead of a WebSocket:

1. `vm.screen.open` opens a tunnel in main and returns a stream id.
2. Main pushes `vm.screen.data`, batched every 16 ms like terminal output.
3. The renderer sends the developer's input with `vm.screen.send` and ends with `vm.screen.close`.

The token stays in main, no port opens, and the CSP is unchanged. The canvas is view-only unless the developer has control.

### MCP tools

`vm_screenshot`, `vm_click`, `vm_move`, `vm_drag`, `vm_scroll`, `vm_type`, `vm_key` and `vm_exec`:

- They are registered once and hidden with `McpSchema.EnabledWhen` while the toggle is off. That covers both `tools/list` and `tools/call`.
- Each starts the thread's VM on first use.
- The pointer and keyboard tools return a screenshot taken 500 ms after acting, which saves the agent a round trip per step.
- While the developer has control, those tools wait, and on hand back they return the current screen without acting.

The credential that names the thread also names its VM, so an agent cannot reach another thread's machine.

### Prompt

`agentInstructions({ tinyVm })` appends a `<tiny-vm>` block only when the toggle is on, and AgentRunner passes the result as `RunTurnInput.instructions`. Claude restarts its session, resuming the same conversation, when the instructions change. Codex and Muse Code receive them every turn.

### Transcript

Screenshots are not stored. AgentRunner drops image data from tool results before it publishes and persists them, and the tool row shows `[image]`.

## Out of scope

- Keeping a thread's VM across a kkcode restart. Sandboxes are disposable and boot in 60 ms, and quitting destroys them.
- Copying the worktree into the VM, or reaching the developer's localhost from it. sbx sandboxes reach only the internet.
- Templates other than `default`, other screen sizes, and full Proxmox QEMU VMs.
- Screenshot thumbnails in the transcript.
- Showing the agent's pointer in the view. noVNC draws only the local cursor.

## Verification

Tests:

- `mcp/server.integration.test.ts` runs the tools against a fake sbxd and a fake VNC server. It checks that the tools are hidden while the toggle is off, that a screenshot comes back as an image, that a click becomes the right RFB events, and that a click waits while the developer has control.
- A test on the runner checks that the instructions carry `<tiny-vm>` only when the toggle is on.

In the real app, use `verify-kkcode` against the real sbx host:

1. Turn the toggle on and screenshot the connection status.
2. Drive the tools with `mcp-call.mjs`, and screenshot the view while they act.
3. Take control and type into the VM, then check that a `vm_click` waits until hand back.
4. Run one short Claude turn that opens a page in the VM.
