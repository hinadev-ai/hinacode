# Link a machine from the CLI by signing in

Status: Building
Date: 2026-11-04

## Problem

`hinacode serve --relay on` printed a URL and a code, and Settings on a desktop had a form to type that code into. Now that people have accounts, the code adds nothing: the URL already says which machine is asking. It is also weak. Eight characters are short enough to guess, and a signed-in person who guesses a pending code can claim someone else's machine.

Serve also exits when nobody opens the link within ten minutes, which kills a server started over SSH or by a service manager.

## User flow

```
$ hinacode serve --relay
Link this machine to your HinaCode account.
Open this URL in any browser, on this machine or another:

  https://relay.hinacode.app/link?code=…

Waiting for you to approve it…
```

1. The person opens the URL. On a machine with a display, serve opens it for them.
2. They sign in with Google or GitHub. Clerk returns them to the same page.
3. They approve `Link home-server to your HinaCode account?`.
4. The terminal prints `Linked.`, and serve continues.

If ten minutes pass first, serve prints a new URL and keeps waiting.

## Design

**Polling is the callback.** The CLI asks `POST /v1/links/claim` every five seconds until the relay has an approval. A callback to a port on localhost, as desktop OAuth apps use, cannot work when the browser is on another machine, so headless would need a second flow. This one works in both.

**The code is a token.** `userCode` is now 16 random bytes in the URL, and nobody reads or types it. The field keeps its name, so released CLIs keep working. `RelayStatus` keeps it too, because released desktops require it when they decode `remote.status` from a newer server, though the UI no longer shows it. The desktop still uses it to approve its own link while signed in.

**One approval click stays.** Signing in does not approve. Otherwise anyone could send a link, and whoever signed in would attach the sender's machine to their account, and their phone and desktop would then connect to it.

**Opening a browser is best effort.** Serve tries only when stdout is a terminal, the session is not SSH, and the platform has a display. A failure changes nothing, because the URL is already printed.

## Out of scope

- A separate `hinacode login` command. Serve is the only CLI path that needs an account.
- Linking a machine without a person, for CI or fleets.

## Verification

- `relay/test/app.test.ts`: codes are long and case-sensitive, and signing in alone does not approve.
- `src/main/remote/relay.integration.test.ts`: an expired link prints a new URL and serve keeps waiting.
- `src/main/serve.test.ts`: the browser command per platform, and none over SSH or without a display.
- By hand: `hinacode serve --relay` against a local relay and a Clerk development instance, approving from a separate browser.
