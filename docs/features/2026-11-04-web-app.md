# HinaCode on the web

Status: Building
Date: 2026-11-04

## Problem

A developer whose machines are linked to the relay can drive them from the desktop app or the phone. Away from both, for example on a borrowed laptop or a work machine where they can't install anything, they have no way in. The phone app shows a reduced UI, so long reviews, diffs, terminals and settings still need the desktop.

## User flow

1. Open `https://code.hinacode.app`. The page asks for the relay owner token, the same one Settings > Connections on the desktop asks for. A relay other than `relay.hinacode.app` can be set under the token field.
2. The page lists every machine the relay shows on the owner's devices. Pick one. That machine becomes the home machine of this browser, and the page remembers it.
3. The full desktop UI loads, running against the home machine. Every other listed machine appears as an environment, as it does on a desktop signed in to the relay.
4. While the home machine is unreachable, a bar at the top says it is reconnecting. Calls wait, as they do on the phone.
5. Settings > Connections shows the relay account and every linked machine. **Sign out** forgets the token and returns to step 1. **Switch machine** returns to step 2. Adding a machine by pairing URL and the Remote section are hidden: the relay adds machines, and turning off remote control on the home machine would cut off the page.

## Design

The renderer already runs in a browser: `site/app` replays it for the marketing site. The desktop's renderer only talks to `window.hinacode`, so the web app is a different `window.hinacode` plus a few branches where a browser cannot do what Electron does.

```
apps/web/src/
  main.tsx        the gate (sign-in, machine picker), then the bridge, then src/renderer/main.tsx
  account.ts      the relay account in localStorage, and GET /v1/machines
  bridge.ts       one Transport per machine, routing, push events, the home status bar
  route.ts        main's environments/route.ts for the browser, on routes.ts and owners.ts
  browser.ts      answers for desktopOnlyMethods a browser can answer
  resources.ts    turns a resource request into an rpc call
public/sw.js      serves /_r/* through the page
```

### Data shape

```ts
// localStorage
"hinacode.relayAccount": { serviceUrl: string; ownerToken: string }
"hinacode.homeMachine": string // environmentId of the machine the browser runs against
"hinacode.clientSettings": ClientSettings

// window.hinacode
HinacodeBridge.runtime: { kind: "desktop" } | { kind: "web"; machine: { id: string; name: string } }
```

`runtime` is the one new field the renderer reads. The preload sets `"desktop"`. Everything a browser cannot do branches on it, not on `environment === null`, because on the web every machine is remote even when the renderer calls it "this machine".

### Connection

Each machine gets the shared `Transport` (`src/shared/transport.ts`), the client the phone has used since the resilient-remote work, with `compact: false` so the server sends full transcripts and never filters by watched thread. An `https:` page can only open `wss://`, so it dials the machine's relay hostname alone. An `http:` page, used in development, dials the direct addresses first, as the phone does.

The desktop never loses its local machine, but the web loses its home machine whenever the network drops. When the home machine comes back, the bridge sends `environment.status` with the home machine's id, and the renderer reloads lists, open transcripts, side chats and terminals as it does for a cloud. `runtime.machine.id` tells the renderer which projects belong to the home machine.

### Routing

`route.ts` is `src/main/environments/route.ts` with the home machine in the place of the local dispatcher. A method in `desktopOnlyMethods` that `browser.ts` answers stays in the browser. Everything else follows `routes.ts`: `named` goes to the named machine or home, `owner` goes to the machine that listed the entity (`owners.ts`), `all` gathers from every machine with the desktop's three-second timeout and last-answer fallback. Pushes from other machines teach owners and get stamped like on the desktop. The home machine's pushes pass through.

A desktop-only method the browser cannot answer goes to the home machine, which answers `DesktopOnly`. That is what the desktop already shows for a cloud.

### Resources

Electron serves attachments, project files and artifacts on custom schemes (`src/main/index.ts`). A browser cannot load those, so on the web `resourceUrl` (`renderer/lib/resourceUrl.ts`) rewrites `hinacode-x://rest` to `/_r/hinacode-x/rest`. The service worker `sw.js` catches `/_r/*` and asks the page over a `MessageChannel`. The page (`resources.ts`) answers with the rpc main uses for a cloud: `attachments.read`, `fs.preview` or `artifacts.file`. External images and GitHub assets load from their own URL.

Chrome does not route a sandboxed iframe's navigation through a service worker. So on the web, artifact and HTML preview frames drop the `sandbox` attribute and get sandboxed by the `content-security-policy: sandbox allow-scripts` header the page sends with every `/_r/` answer. Every answer carries it, attachments included, so a resource opened as its own tab runs in an opaque origin too and cannot read the owner token. The sandboxed document has an opaque origin, so the worker does not control it either. The page therefore inlines the files the document links with a relative `src` or `href` as data URLs before sending it.

### Renderer branches on `runtime === "web"`

- No traffic-light padding on a Mac.
- The project dialog hides Browse, as it already does for a cloud.
- The artifact export menu is hidden.
- The browser panel and the Boat VM use their remote variants (`RemoteBrowserPage`, an iframe) instead of `<webview>`.
- The composer's file picker is an `<input type="file">`, and `pathForFile` is empty, so every file goes inline.
- Reveal in Finder and Open with are hidden.
- Settings > Connections hides Add environment and Remote, and shows Switch machine.

### Trust

The owner token lives in the browser's localStorage, as on the relay's link page. The relay allows CORS for `/v1/*` only from `WEB_ORIGINS`. The page never sends the pairing token: the transport proves it with the challenge from ADR 0022. `code.hinacode.app` sends `frame-ancestors 'none'`.

## Out of scope

- Real accounts. The owner token is the sign-in until Clerk replaces it (ADR 0021).
- URLs that follow the route. The router keeps memory history, as on the desktop.
- Live file trees and the VNC screen. `fs.watch` and `vm.screen.open` need the desktop, as they do for a cloud.
- GitHub user-attachment images in private repositories, which main fetches with the user's GitHub token.
- Files an artifact loads at runtime with `fetch` or CSS `url()`. Only the files its HTML links are inlined.
- Artifact export. It writes a file on the machine that runs the desktop.
