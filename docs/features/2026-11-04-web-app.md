# HinaCode on the web

Status: Building
Date: 2026-11-04

## Problem

A developer whose machines are linked to the relay can drive them from the desktop app or the phone. Away from both, for example on a borrowed laptop or a work machine where they can't install anything, they have no way in. The phone app shows a reduced UI, so long reviews, diffs, terminals and settings still need the desktop.

## User flow

1. Open `https://code.hinacode.app`. The page asks for the relay owner token, the same one Settings > Connections on the desktop asks for. A relay other than `relay.hinacode.app` can be set under the token field.
2. The full desktop UI loads with every machine the relay shows on the owner's devices. The browser is not a machine, so there is no "This machine". Every project, picker and settings page names the machine it belongs to, as the desktop does for a cloud.
3. While a machine is unreachable, the sidebar and Machine resources mark it, as they do for a cloud on the desktop. Calls to it wait, as they do on the phone.
4. Settings > Connections shows the relay account and every linked machine. **Sign out** forgets the token and returns to step 1. The page hides Add environment, because the relay adds machines, and the Remote section, because there is no local listener to configure.

## Design

The renderer already runs in a browser. `site/app` replays it for the marketing site. The desktop's renderer only talks to `window.hinacode`, so the web app is a different `window.hinacode` plus a few branches where a browser cannot do what Electron does.

```
apps/web/src/
  main.tsx        the sign-in gate, then the bridge, then src/renderer/main.tsx
  account.ts      the relay account in localStorage, and GET /v1/machines
  bridge.ts       one Transport per machine, routing, push events
  route.ts        main's environments/route.ts for the browser, on routes.ts and owners.ts
  browser.ts      answers for desktopOnlyMethods a browser can answer
  resources.ts    turns a resource request into an rpc call
public/sw.js      serves /_r/* through the page
```

### Data shape

```ts
// localStorage
"hinacode.relayAccount": { serviceUrl: string; ownerToken: string }
"hinacode.clientSettings": ClientSettings

// window.hinacode
HinacodeBridge.runtime: { kind: "desktop" } | { kind: "web" }
```

`runtime` is the one new field the renderer reads. The preload sets `{ kind: "desktop" }`. On the web every project carries a machine's `environmentId`, so the renderer takes the paths it already has for a cloud. It branches on `runtime` only where the null environment would show up anyway: the pickers and machine lists that offer "This machine", and what a browser cannot do.

### Connection

Each machine gets the shared `Transport` (`src/shared/transport.ts`), the client the phone has used since the resilient-remote work, with `compact: false` so the server sends full transcripts and never filters by watched thread. An `https:` page can only open `wss://`, so it dials the machine's relay hostname alone. An `http:` page, used in development, dials the direct addresses first, as the phone does.

Every status change is sent as `environment.status`. When a machine comes back, the renderer reloads its lists, open transcripts, side chats and terminals, as it does for a cloud.

### Routing

`route.ts` is `src/main/environments/route.ts` with no local dispatcher. Every method in `desktopOnlyMethods` stays in the browser. Everything else follows `routes.ts`: `named` goes to the named machine, `owner` goes to the machine that listed the entity (`owners.ts`), and `all` gathers from every machine with the desktop's three-second timeout and last-answer fallback. Every push teaches owners and gets stamped with its machine, as on the desktop.

A call that names no machine, such as `settings.get` at startup, goes to the first connected machine, as on the phone. A desktop-only method the browser cannot answer, such as `fs.watch`, gets `DesktopOnly` from the router and never leaves the page. That is the error the desktop already shows for a cloud, and it keeps the web a client: it reaches a machine only through rpc that machine serves.

### Resources

Electron serves attachments, project files and artifacts on custom schemes (`src/main/index.ts`). A browser cannot load those, so on the web `resourceUrl` (`renderer/lib/resourceUrl.ts`) rewrites `hinacode-x://rest` to `/_r/hinacode-x/rest`. The service worker `sw.js` catches `/_r/*` and asks the page over a `MessageChannel`. The page (`resources.ts`) answers with the rpc main uses for a cloud: `attachments.read`, `fs.preview` or `artifacts.file`. External images and GitHub assets load from their own URL.

Chrome does not send the navigation of an iframe sandboxed without `allow-same-origin` through a service worker. So on the web, artifact and HTML preview frames get `sandbox="allow-scripts allow-same-origin"`, and the `content-security-policy: sandbox allow-scripts` header on every `/_r/` answer takes the origin away, as Electron's handlers do. The attribute stays on the frame, so a page the frame navigates to still cannot open popups or navigate the app. Attachments get the header too, so a resource opened in its own tab also runs in an opaque origin and cannot read the owner token.

The worker does not control a document with an opaque origin, so a framed page cannot load its sibling files through `/_r/`. Before sending an HTML document to a frame, the page inlines every file it links with a relative `src` or `href` as a data URL.

### Renderer branches on the web runtime

- No traffic-light padding on a Mac.
- The project dialog hides Browse, as it already does for a cloud.
- The artifact export menu is hidden.
- The browser panel and the Boat VM use their remote variants (`RemoteBrowserPage`, an iframe) instead of `<webview>`.
- The composer's file picker is an `<input type="file">`, and `pathForFile` is empty, so every file goes inline.
- Reveal in Finder and Open with are hidden.
- The Where field, the settings machine picker, Machine setup and Machine resources leave out "This machine".
- Settings hides Add environment, Remote, Version and the font pickers, and the notification notice points at the browser.

### Trust

The owner token lives in the browser's localStorage, as on the relay's link page. The relay allows CORS for `/v1/*` only from `WEB_ORIGINS`. The page never sends the pairing token. The transport proves it with the challenge from ADR 0022. `code.hinacode.app` sends `frame-ancestors 'none'`.

## Out of scope

- Real accounts. The owner token is the sign-in until Clerk replaces it (ADR 0021).
- URLs that follow the route. The router keeps memory history, as on the desktop.
- Live file trees and the VNC screen. `fs.watch` and `vm.screen.open` need the desktop, as they do for a cloud.
- GitHub user-attachment images in private repositories, which main fetches with the user's GitHub token.
- Files an artifact loads at runtime with `fetch` or CSS `url()`. Only the files its HTML links are inlined.
- Artifact export. It writes a file on the machine that runs the desktop.

## Verification

- `apps/web/src/route.test.ts` covers routing. `src/shared/transport.test.ts` covers `compact: false`. `relay/test/app.test.ts` covers CORS.
- `pnpm test:e2e:web` runs `apps/web/e2e`, a Playwright suite of its own: a real `hinacode serve`, a stub relay and the built web app in Chromium. `client-only.spec.ts` holds the rule above. It walks the app and every settings page, and fails when a desktop-only method reaches a machine, the page loads a `file:` or `hinacode-*:` URL, a control offers "This machine" or a local file, or client settings leave `localStorage`.
- By hand: `hinacode serve` on two ports, `wrangler dev` for the relay with both machines published, and `pnpm --filter hinacode-web dev`. Sign in, see both machines' projects, open a thread on each, send a message, paste an image and open a terminal. Stop a machine and see it marked offline, start it again and see it come back.
