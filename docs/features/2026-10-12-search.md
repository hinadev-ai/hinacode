# Search

Status: Building
Date: 2026-10-12

## Problem

A long agent transcript is hard to scan. A developer who wants "the place where it ran the migration" scrolls and reads. Across many threads and projects there is no way to ask which thread touched `Worktrees.ts`, or which file in the workspace holds a symbol, without leaving the app.

## User flow

Find in thread:

1. In a thread, press `mod+f`. A find bar appears above the transcript with its field focused. If it was already open, the field is focused and its text selected.
2. Type. After 100 ms the transcript marks every match, the bar shows "3 of 12", and the last match (nearest the end, where the reader usually is) scrolls to the middle of the view.
3. Enter goes to the next match, shift+Enter to the previous one, and the arrow buttons do the same. Rows the virtual list has not mounted are scrolled to first, then marked.
4. Escape or the close button hides the bar and returns focus to where it was, or to the composer.

Global search:

1. Press `mod+shift+f` anywhere. The command palette opens in search mode (prefix `%`), so typing `%` in the palette gets there too.
2. Type. Results come in two groups: Threads, one row per matching message with the thread title and a snippet, newest first; then Files, one row per matching line in the open thread's workspace with the path, line and the line's text. The match is highlighted in each row.
3. Enter on a thread result opens that thread with the find bar open on the same query, at the match in that message. Enter on a file result mentions `@path` in the open thread's draft, as the composer's `@` completion does.
4. Without an open thread there is no Files group. If `rg` is not installed, the Files group shows one row asking the user to install ripgrep.

## Design

### Find in thread

`MessageList` is a virtualized `LegendList`, so the DOM only holds the rows on screen. Two options were prototyped on a synthetic 2,000-message thread:

- (a) Search the transcript in the `useMessages` store with a pure `findMatches(messages, query)`, scroll the list to the match's message, then mark matches while rendering. `findMatches` takes 0.3 to 0.8 ms per query (7,870 hits for "migration").
- (b) Turn virtualization off and use `webContents.findInPage`. Rendering every row's markdown alone, without DOM, layout or paint, takes 309 ms, a lower bound paid every time the bar opens, and the thread loses virtualization while it is open.

(a) is chosen. The pieces:

- `lib/find.ts`: `findPattern(query)` (literal, case-insensitive, Unicode) and `findMatches`, which searches what the collapsed transcript shows: message text, a tool call's name and one-line summary, and a file change's path. Reasoning, tool input and output, and diffs sit behind a disclosure and are not searched. Reply text the agent is still writing is not on screen yet, so it is skipped.
- `lib/toolCall.ts`: `describeToolCall`, moved out of `MessagePart.tsx` so the find logic and the row agree on the summary.
- `components/FindHighlight.tsx`: a `FindPatternContext` holding the active pattern, `Highlighted` for plain text, and a rehype plugin that wraps matches in rendered markdown in `<mark data-find-match>`. Fenced code is marked by `Highlighted` because `Markdown` renders it from the raw source.
- `components/FindBar.tsx`: the bar, as a `search` landmark with a labelled input and a live `output` for the count. It scrolls with `scrollToIndex`, waits up to 10 frames for the row to mount, then picks the nth `<mark>` in that row and sets `data-current` on it.
- `stores/ui.ts`: `findThreadId`, `findQuery`, `findMessageId` and a focus request counter, so the `search.find` command and global search can open the bar.
- Marks use the tokens `--color-find-match`, `--color-find-match-current` and `--color-find-match-ring`, mixed from `--syntax-token`, so they follow the theme. The current mark changes over 150 ms and not at all under reduced motion.

### Global search

Main process, one Effect service `services/Search.ts` and two rpc methods:

```ts
"search.threads": { query: string; limit?: number } -> Array<{ threadId; threadTitle; projectId; messageId; snippet; at }>
"search.files": { threadId: string; query: string; limit?: number } -> Array<{ path; line; column; text }>
```

**Threads.** Migration `0008_messages_fts` adds an FTS5 table `message_fts(body)` with the trigram tokenizer, keyed by the message rowid and kept in sync by insert, update and delete triggers on `message`. `body` is extracted from the `parts` JSON in SQL: text parts, a tool call's name and summary field, and a file change's path, matching what find in thread searches. The migration backfills existing messages.

Measured on a seeded database of 50,000 messages across 500 threads (105 MB without an index), with Electron's `node:sqlite` (SQLite 3.53.4, FTS5 built in):

| Approach                            | Query with hits | Query with no hits                                     | Extra size  |
| ----------------------------------- | --------------- | ------------------------------------------------------ | ----------- |
| `LIKE` over the extracted text      | 0.4 to 0.5 ms   | 136 ms                                                 | 0           |
| `LIKE` over the raw `parts` JSON    | 0.04 ms         | 45 ms, and it matches JSON keys and hidden tool output | 0           |
| FTS5 `unicode61`, `MATCH`           | 0.2 ms          | 0.01 ms                                                | about 20 MB |
| FTS5 `trigram`, body stored, `LIKE` | 0.14 to 0.5 ms  | 0.02 ms                                                | 117 MB      |

`unicode61` is the smallest and fastest, but it matches whole tokens. "Worktree" would not find "Worktrees.ts", and a run of Chinese or Japanese text is one token, so "遷移" would not find "遷移完成". Trigram gives the same substring semantics as find in thread, in any script. The body is stored rather than contentless because FTS5 evaluates `LIKE` against stored column values, and `LIKE` covers queries of one or two characters too. A pattern under three characters, or one that needs `ESCAPE` because the query contains `%` or `_`, cannot use the index and scans the table in 30 to 35 ms. The cost is disk, about as much again as the transcript text, and a one-time backfill of 7 to 11 s for 50,000 messages (about 1 s for a more typical 5,000).

Snippets are an 80-character window around the first match, cut in TypeScript, because FTS5's `snippet()` works in tokens and trigram tokens cut words apart.

**Files.** `search.files` names a thread, not a path. Main resolves the thread's active workspace (worktree or project root) the same way `files.list` does, so no renderer-supplied path reaches a child process, and an unknown thread fails with `NotFoundError`. It runs `rg --json --fixed-strings --smart-case --max-count 50 -e <query> <root>`, stops reading after `limit` matches (default 100), and kills `rg` after 3 s. The query is literal, as in find in thread. `rg` is found on PATH or through a login shell, as the agent binaries are, because a GUI-launched app gets a minimal PATH. If it is not found the call fails with a tagged `RipgrepMissing`. There is no fallback to walking the tree in JavaScript.

**UI.** Search is one more `PaletteMode` in `palette/modes.ts` with prefix `%`, two sources in `palette/search.tsx`, and a `rank` function that keeps the server's order and highlights the literal match instead of fuzzy matching. `search.global` (`mod+shift+f`) opens the palette in that mode. The files source waits 150 ms after the last keystroke so typing does not start a ripgrep per character. Sources share pending requests only; repeating a query after the previous request settles reads current messages and files.

## Out of scope

- Regex and whole-word search. Both features take the query literally.
- Searching reasoning, tool output and diffs. They are hidden in the transcript, so a hit there would point at nothing visible.
- Searching files in a project without opening one of its threads. The palette's file results are scoped to the open thread's workspace, and search follows that.
- Replace.

## Verification

- `lib/find.test.ts` covers `findMatches`: case-insensitive literal matching, reading order, what is and is not searched, and text still streaming.
- `services/Search.integration.test.ts` runs against a real SQLite file and a real temp git repo: thread hits with snippets, updates and deletes reaching the index, a short query, an unknown thread, file hits with line and column, and a missing `rg`.
- With `verify-kkcode`: seed a thread with a long transcript, press `mod+f`, type a word, step through matches and check the count and the marked row. Press `mod+shift+f`, type a word that appears in a thread and in a file, open each kind of result. Screenshots in light and dark.
