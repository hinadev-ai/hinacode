# Open with

Status: Shipped
Date: 2026-10-20

## Problem

A thread works in a worktree whose path nobody remembers. To read or edit its code in their own editor, a developer opens Show in folder, then drags the folder onto Cursor or types `cursor <path>` in a terminal. The same goes for one file they just saw in the Files view.

## User flow

1. The thread header shows the app used last, with its own icon. One click opens the thread's worktree, or the project root, in it.
2. The chevron next to it lists every supported app installed on this desktop, then Show in folder. Picking one opens the folder and makes that app the one-click choice.
3. The project's "…" menu and the Files view's right-click menu have an Open with submenu. For a file, it lists only editors, because terminals open folders.
4. When the app has gone since the list loaded, a toast says it could not open.

Cloud threads show none of this, because their paths exist only on that machine.

## Design

- `OpenerId` in `shared/domain.ts` is a closed list: VS Code, Cursor, Windsurf, Zed, Sublime Text, Xcode, Terminal, iTerm, Ghostty and Warp. `src/main/openers.ts` maps each one to its macOS bundle and its CLI on Linux and Windows.
- `shell.openers` lists the installed ones with a QuickLook icon on macOS. `shell.openWith` takes a path and an `OpenerId`, so the renderer cannot name an arbitrary program. macOS runs `open -a <bundle> <path>`, and other platforms spawn the CLI found on `PATH`. Both are desktop-only methods.
- `ClientSettings.openWith` keeps the app used last.

## Out of scope

- Opening a file at a line. Each editor has its own syntax (`--goto`, `file:line`), and nothing in the app points at a line yet.
- A setting to add custom apps. The list is short, and an unknown app can still be reached through Show in folder.

## Verification

Launch an instance, open a thread, and pick each app from the header chevron. Then right-click a file in Files and open it in an editor. `shell.openers` over rpc lists what is in `/Applications`.
