# The `hinacode` CLI

Status: Building
Date: 2026-11-02

## Problem

Scripts, CI jobs, editors and other programs on a machine running HinaCode had no way to start a thread, wait for it, or see what it needs. They could only go through the window or the phone.

## Principles

1. **Headless.** The CLI is for programs, not people at a prompt. Every command prints one JSON document and exits, except `watch`, which streams NDJSON. There are no prompts, colours or TTY modes.
2. **One socket, every machine.** The CLI talks to the HinaCode on this machine. The desktop already reaches every paired cloud, so the CLI does too, with no pairing step.
3. **The contract is the CLI.** Output is encoded with the rpc schemas, and `hinacode rpc` reaches every method. The CLI holds no API of its own, so it can't drift from the app.
4. **Where you stand is the default.** The project comes from the current directory. `.` means the thread whose worktree you are in.

## User flow

### Start a thread

```sh
$ cd ~/code/app
$ hinacode run "make the login test stop flaking"
{"threadId":"a41f09c2-…","title":"thread-a41f0","projectId":"…"}
```

`run` returns as soon as the prompt is sent. The thread shows up in the app at once, and runs there like any other.

- `run` creates a separate thread through `threads.create`, then calls `threads.update` for agent settings and `threads.send` with the workspace. Each run gets its own thread, so concurrent CLI calls and the desktop composer's draft remain independent.
- The project is the one whose root, or one of whose worktrees, contains the current directory. If none does, `run` exits 64 and says to add the project in the app or pass `--project <id|path>`. It never imports a folder on its own.
- The workspace follows the project's default, like the composer. `--worktree` and `--here` override it. `--from <ref|#pr>` picks the branch or pull request to start from.
- `--machine <name>` runs in that machine's project for the same GitHub repository. `--provider`, `--model`, `--effort` and `--access` set the agent. `--attach <file>` (repeatable) goes through `attachments.stage`.
- The prompt comes from the argument, from piped stdin, or from both: `git diff | hinacode run "review this"`.

### Wait for the outcome

```sh
hinacode run --wait "bump deps and fix breakage"
case $? in
  0) echo done ;;
  2) echo "needs a human" ;;
  *) echo failed ;;
esac
```

`--wait` blocks until the turn ends or asks for something, then prints `{"threadId","title","outcome","message"?}`. The outcome is `done`, `failed`, `needsHuman` or `limited`, and the exit code matches. A run that asks for an approval, an answer or a secret ends the wait with `needsHuman`. The ask stays open for the desktop, the phone, or a script that answers it. `send` takes `--wait` too.

### Steer, stop and read

```
hinacode send <thread> "<text>"   # steer if running, else start a turn; --queue to queue
hinacode stop <thread>            # interrupt the turn
hinacode open <thread>            # show the thread in the desktop window
hinacode ls                       # threads, filtered by --project . --machine --status
hinacode log <thread>             # the transcript
hinacode machines                 # the machines this HinaCode reaches
hinacode inbox                    # what is waiting on a human: {"asks","running","idle"}
hinacode watch                    # every machine's notices as NDJSON, until killed
```

`send` follows the composer's rule: a running thread gets the text as steering, and an idle one starts a turn with it.

A thread reference is a full id, a 4+ character prefix, or `.`. A prefix that matches more than one thread is an error listing the matches.

`inbox` lists each pending approval, question and secret request with its request id, plus threads stopped at a usage limit. A script answers through the rpc methods the app uses, such as `hinacode rpc approvals.respond '{"requestId":"…","decision":"allow"}'`. `watch` prints `turn_completed`, `turn_failed`, `turn_limited` and the three asks as they happen, one `PushEvent` per line, for a notifier.

### The escape hatch

```
hinacode rpc threads.usage '{"threadId":"a41f…"}'
hinacode rpc --list
```

Every method in `RpcMethods` is reachable. The payload is decoded against the method's request schema before it leaves the CLI. A new rpc method works from the CLI the day it lands. A method becomes a named command only after people keep reaching for it through `rpc`.

## Design

### Data shapes

```ts
type ThreadRef = { kind: "id"; id: string } | { kind: "prefix"; prefix: string } | { kind: "here" }

type Outcome = "done" | "failed" | "needsHuman" | "limited"

type Ask =
  | { kind: "approval"; threadId: string; request: ApprovalRequest }
  | { kind: "question"; threadId: string; request: QuestionRequest }
  | { kind: "secret"; threadId: string; request: SecretRequest }
  | { kind: "limited"; thread: Thread }

const EXIT = {
  done: 0,
  failed: 1,
  needsHuman: 2,
  limited: 3,
  unreachable: 4,
  usage: 64,
} as const
```

- `here` resolves through `worktrees.list`. It is the thread whose worktree contains the current directory. Archived threads and side chats don't count.
- `Outcome` comes from one pure function over a thread's pushes: `turn_completed`, `turn_failed`, `turn_limited`, or any `*_requested` ask.
- `Ask` is an inbox row. `asksFrom` builds the rows from `threads.list` and each waiting thread's `threads.transcript`.
- `EXIT` is the only place exit codes are defined. Its first four keys are the outcomes, so a script's `case` and the printed outcome can't diverge.

### Transport: a local socket that routes

The desktop and the cloud each listen on `<dataDir>/run/cli.sock`. It speaks the remote protocol (`ClientFrame` and `ServerFrame` in `src/shared/remote.ts`) over the same `ws` server code as the phone listener. Both listeners share `src/main/remote/session.ts` for call keys, heartbeats, `watch` filtering and `ready`.

- **No token.** File permissions are the boundary. The listener creates `run/` and resets it to 0700, refuses to start if another user owns it, and sets the socket to 0600. Someone who can open it already has the user's shell, which is out of scope. The folder carries the protection on macOS too, which ignores a socket file's own mode. The listener sends `ready` as soon as a client connects. A client that gets `challenge` instead knows it reached the wrong socket.
- **Deep data folders.** A socket path has to fit in about 104 bytes. A data folder too deep for that, such as a test instance inside a worktree, gets its socket in the temp dir instead: `hinacode-<uid>/<sha256 of the data folder>.sock`, with the same ownership rule. `cliSocketPath` in `src/main/remote/cliSocketPath.ts` is the one function both sides use.
- **Calls go through `route`, not `dispatch`.** The CLI listener calls `route` from `src/main/environments/route.ts`, the same function Electron IPC uses. `threads.list` merges every paired cloud, and a thread id is forwarded to the machine that owns it.
- **Events mirror the windows.** `WindowBroadcast` in `src/main/services/Events.ts` carries everything windows receive, including cloud pushes. The socket always sends them compacted, so long tool output stays on the server until `log` or `rpc threads.toolOutput` asks for it.
- **Desktop-only methods stay refused.** `hinacode open` uses `threads.reveal` instead. It routes to the thread's owner and publishes a `thread.reveal` push. The desktop's main window navigates to the thread and calls `app.focus` itself, which also works when a cloud owns the thread.

The CLI tries these data folders in order and connects to the first live socket:

1. `--data <dir>`, which is tried alone, or `HINACODE_USER_DATA`.
2. `~/.hinacode`, the packaged desktop.
3. `~/.hinacode-dev`, the desktop run from source.
4. `~/.hinacode-cloud`, `hinacode serve`.

With none live, it exits 4 with `HinaCode isn't running here. Open the app, or start a cloud with hinacode serve.`

Every mutation carries a fresh `key`, so the server's `call-keys` table runs it once. The CLI doesn't reconnect. A local socket only drops when HinaCode quits, and then the command exits 4.

### Process layout

- `bin/hinacode.mjs` imports `out/server/cli.js`. `serve` and `pair` reach the daemon through a dynamic `import()`, so other commands never load the app layer, SQLite or the agent SDKs. They start in about 100 ms.
- Commands are declared with `effect/cli`, which ships with the `effect` version we already use. Help, `--version`, `--completions <shell>` and argument errors come from the declarations. `serve` and `pair` are declared the same way, with their existing flags and environment variables.
- stdout carries exactly one JSON document per command, on one line, encoded with the rpc schemas. `watch` is the one exception and prints NDJSON. Errors go to stderr as `hinacode: <message>` with an exit code from `EXIT`.
- Error and help text is plain English in `src/cli`. It stays out of the Paraglide catalogs, because the app's locale switch doesn't reach a shell.

### Trust boundaries

- Every frame the CLI receives decodes with `ServerFrame`. Every request encodes with its method's schema before it is sent, and every answer decodes with the response schema.
- A script answering a secret request passes the value through `hinacode rpc secrets.respond`. Feed the payload on stdin rather than argv to keep it out of shell history and process listings.
- The CLI writes no state of its own. It has no config file, token store or cache, so there is nothing to leak or migrate.

| Command               | rpc                                               | Flags                                                                                                                             |
| --------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `inbox`               | `threads.list`, `threads.transcript`              |                                                                                                                                   |
| `run [prompt]`        | `threads.draft`, `threads.update`, `threads.send` | `--wait`, `--worktree`, `--here`, `--from`, `--machine`, `--provider`, `--model`, `--effort`, `--access`, `--attach`, `--project` |
| `send <ref> <text>`   | `threads.steer`, `threads.send`, `threads.queue`  | `--queue`, `--wait`                                                                                                               |
| `stop <ref>`          | `threads.interrupt`                               |                                                                                                                                   |
| `open <ref>`          | `threads.reveal`                                  |                                                                                                                                   |
| `ls`                  | `threads.list`                                    | `--project`, `--machine`, `--status`                                                                                              |
| `log <ref>`           | `threads.transcript`                              |                                                                                                                                   |
| `machines`            | `machines.list`                                   |                                                                                                                                   |

`--help`, `--version`, `--completions <shell>` and `--data <dir>` work everywhere. There are no aliases and no hidden commands.

## Out of scope

- **A CLI for agents.** Agents already have the hinacode MCP server, with credentials scoped to one thread (ADR 0007, ADR 0013). A second agent surface would split the tool set and hand agents a socket that isn't scoped to their thread. The socket is for humans and their scripts.
- **Dialling a remote machine directly.** The desktop or the local cloud is the hub. To drive a cloud from a laptop, run the desktop. Over SSH, run `hinacode` on the cloud. A token store and pairing from the terminal can come later if people ask for them.
- **Windows.** Node can't set a DACL on a named pipe, and the default lets other local users read it. The socket ships on macOS and Linux.
- **An interactive mode.** No live inbox, prompts, transcript streaming or `attach`. People use the desktop or the phone, and `hinacode open` gets them there.
- **Managing projects, automations, accounts and settings** as named commands. `hinacode rpc` covers them.

## Verification

- `src/main/remote/cliSocket.integration.test.ts` runs a desktop with a paired cloud. It checks that a client gets `ready` without auth, that `threads.list` includes the cloud's thread, that a cloud event reaches the socket, that `threads.reveal` on a cloud thread comes back as a push, that desktop-only methods are refused, the 0600 socket and 0700 folder, a 0755 data folder, a data folder too deep for a socket path, and the socket's removal on shutdown.
- `src/cli/run.integration.test.ts` runs the real app layer with a scripted agent. It checks that `run` returns the thread id, that `run --wait` ends `done` with exit 0 and `needsHuman` with exit 2 on an approval, that `inbox` lists the approval, and that answering it lets the turn finish.
- Unit tests cover thread references, project resolution, socket candidates, the socket path rule, the client against a real `ws` server, ask rows, and the outcome mapping.
- With `verify-hinacode`, start a desktop with `HINACODE_MOCK_CLAUDE=approvals`. Start a run from the CLI, see it in the sidebar, answer its approval with `hinacode rpc approvals.respond`, see the desktop's approval card clear, and bring the thread up with `hinacode open`.
