# Side chat

Status: Shipped
Date: 2026-10-30

## Problem

While an agent works through a long turn, the developer often wants to ask something about it: why it picked an approach, what a file it read does, whether a test it skipped matters. Today the only ways are to steer the running turn, which derails it, or to queue the question behind the turn. Claude Code solves this with `/btw`. HinaCode runs three agents and should offer the same thing to all of them.

## User flow

1. A thread is running. The developer clicks the side chat button in the side panel's activity bar, picks "Side chat" in the command palette, or types `/sidechat` in the composer.
2. The side panel opens on the side chat view with its own composer focused. `/sidechat why X?` opens it and sends the question in one step.
3. The question goes to a fork of the thread's agent session. The main turn keeps running.
4. The side chat keeps its history while the panel is closed. "New side chat" discards it, and the next question forks the thread again from where it is now.

## Design

- A side chat is a thread with `side_of` set to its parent. `thread.side_of` references `thread(id)` with `ON DELETE CASCADE` and has a unique index, so a thread has at most one side chat and deleting the parent removes it.
- `Threads.list` leaves side chats out, so the sidebar, the phone, MCP `list_threads` and other machines never see them. `threads.sidechat({ threadId })` gets or creates the parent's side chat. Discarding one is `threads.delete`.
- The side chat copies the parent's agent, model, account and worktree, and runs with `supervised` access so it cannot change files without an approval. A chat project's side chat runs in the chat's folder. Worktree removal ignores the owner's own side chat when it checks for other open threads.
- The fork is resolved when the first side chat turn starts, not when the panel opens, so a question asked minutes later still sees the latest state. The side chat keeps a model picked in its own composer unless the parent has since switched agents. `latestForkPoint` in `src/main/agents/sidechat.ts` picks the parent's newest fork point that belongs to its current agent, the same checkpoint "Fork" on a message uses. The runner writes it to the side chat as `forkedFrom`, and the existing fork path resumes from it: `forkSession` plus `resumeSessionAt` for Claude, `thread/fork` for Codex.
- Messages after that checkpoint belong to the running turn, which the provider session has not committed yet. `sidechatPrompt` renders them with the handoff transcript renderer ahead of the question. Muse has no fork points, so its side chat gets the whole thread that way.
- The prompt tells the agent it is in a side chat and the main agent is still working in the same worktree, so it should answer and leave files alone.
- The renderer keeps side chats in `useThreads.sidechats`, keyed by parent id, so every selector over `byId` stays as it was. The side chat view reuses the transcript, the pending request cards and the composer.

## Out of scope

- More than one side chat per thread. A second question goes in the same side chat.
- Sending the side chat's answer back to the main thread. Copy and paste works, and steering exists for that.
- Read-only enforcement beyond `supervised` access. A side chat that asks to edit shows an approval card like any thread.

## Verification

- `sidechat.test.ts` covers the fork point choice and the rendered prompt.
- `Threads.integration.test.ts` covers get or create under a race, the list leaving side chats out, the cascade, the rebase, the chat folder, and archiving a parent whose side chat shares its worktree.
- `AgentRunner.integration.test.ts` opens a side chat while a turn waits on an approval and checks the fork checkpoint, `supervised` access and the running turn in the prompt.
- `stores/threads.test.ts` covers routing side chats out of `byId`.
- With `verify-hinacode`: start a long Claude turn, open the side chat, ask what the agent is doing, and screenshot the answer next to the running turn.
